# Разбор кода SwapOwl: с чего начать и где что лежит

Документ для того, кто хочет понять систему за 30 минут: что внутри, как устроены главные потоки, чем гарантируется
корректность и где это проверяется. Каждая ссылка на код — путь от корня репозитория.

## 1. Что это и как устроено

SwapOwl — автономная система учёта остатков и сроков годности для ресторана: что истекает, что в стоп-листе, что
продвигать и что заказать, в рублях. Она **не надстройка над iiko**: у неё свой склад и свои партии; с iiko, кассами и
накладными она обменивается через адаптеры (`cmd/iiko-adapter`, `docs/iiko.md`).

Один процесс API (`cmd/api`) на PostgreSQL, фронтенд — статика (React), рядом необязательные процессы: бот
уведомлений, адаптер iiko, хаб сети, watchdog, симулятор.

```
            ┌───────────────┐   HTTP + SSE    ┌──────────────────────────────┐
  браузер ─▶│ web (frontend)│────────────────▶│ cmd/api                      │──▶ PostgreSQL
  mini-app  └───────────────┘                 │  internal/api  (HTTP, роли)  │
  бот ──────────────────────────────────────▶ │  internal/domain (чистая     │
  iiko-adapter / кассы ─────────────────────▶ │    логика, без БД и часов)   │
                                              │  internal/store (транзакции) │
                                              │  janitor · events · clock    │
                                              └──────────────────────────────┘
```

Ключевое решение: **вся бизнес-логика — чистые функции** в `internal/domain` (ни БД, ни часов, ни сети): FEFO,
стоп-лист, риск партий, спрос, поставки. `internal/store` только читает данные в структуры и вызывает эти функции
внутри транзакции. Поэтому логику можно проверять таблицами и свойствами, а БД — отдельными сторожами.

## 3. Главные потоки

### 3.1. Заказ: «всё или ничего», одним транзакционным проходом

`POST /api/orders` → `internal/api/orders.go` суммирует потребность по всем блюдам заказа (с проверкой переполнения
`units.Mul/Add`) → `store.PlaceOrder` (`internal/store/orders.go`):

1. вставка заказа по `id` (идемпотентность: повтор с тем же телом возвращает сохранённый ответ, с другим — `409`);
2. **пауза блюда**: блюдо на ручной паузе → заказ отклоняется целиком, склад не тронут;
3. блокировка продуктов `SELECT … FOR UPDATE` **по одному, по отсортированным id** (`store.LockProducts`) — единый
   порядок исключает взаимные блокировки;
4. чтение времени и партий (`remaining > 0 AND now < expires_at`);
5. `domain.PlanWriteoff` — план FEFO либо нехватка, **не оба**;
6. относительные `UPDATE batches SET remaining = remaining − …` с условием и запись движений `sale`;
7. отказ тоже сохраняется (причина — по каким продуктам не хватило).

Стоп-лист — **не хранится**: `domain.StopList(dishes, available)` чистая функция остатков, поэтому он не может
разойтись со складом. Ручная пауза блюда — отдельное решение менеджера поверх этого (таблица `dish_holds`).

### 3.2. FEFO и срок годности

Списание идёт с партии с ближайшим `expires_at` (при равенстве — с меньшим `id`), следующая — только после
исчерпания предыдущей. «Годен до даты D» значит «доступно до начала дня D+1 по времени ресторана»
(`internal/domain`, часовой пояс из `RESTAURANT_TZ`). Партия доступна при `now < expires_at` **независимо от
фонового прохода**: «дворник» (`internal/janitor`) лишь записывает списание «истёк срок» в момент `expires_at`.

### 3.3. Поставка и приёмка

`POST /api/deliveries`: срок годности **обязателен** (иначе `400`), поставка идемпотентна по `id`. Приёмка сканом
читает «годен до» из маркировки (GS1, AI 17) — `frontend/src/lib/gs1.ts`; позиция без кода вводится вручную.
Вскрытие упаковки создаёт дочернюю партию с `expires_at = min(срок, now + срок_после_вскрытия)` (`domain/opened.go`).

### 3.4. Горячие предложения, витрина, лестница спасения

- `hotoffers/a`: «требуемый темп» — какое блюдо и сколько порций надо продать до срока, чтобы партия разошлась.
- `hotoffers/b`: жадное распределение между блюдами с предохранителем (не опустошить дефицитный продукт).
- Рядом считаются маржа порции (`api/hotoffers.go`), «витрина» (`api/rescue.go`) и **лестница** (`api/ladder.go`):
  по каждой партии — ступени «продать», «скидка», «заготовка» (roadmap), «передать» (сеть) в рублях.
- Спрос: `λ = (prior·n0 + запрошено)/(n0 + активные сутки)`; точность прогноза проверяется бэктестом
  (`domain/demand_backtest.go`, `GET /api/analytics/forecast-accuracy`).

### 3.5. Реальное время

Шина `internal/events` рассылает `stock.changed`, `stoplist.changed`, `hotoffers.changed`, `clock.changed`,
`batch.expiring` и т.д. по SSE (`GET /events`). Фронтенд подписывается через `useLive`, бот — своим подписчиком.
Событие «партия истекает» шлётся один раз на партию, в том числе после рестарта и прыжка времени.

### 3.6. Доступ и Telegram

Роли `viewer < operator < admin`, сессионная cookie и ключи интеграции (`internal/auth`). Mini-app входит по
подписи Telegram (`initData`, HMAC), привязка к веб-аккаунту — по одноразовому коду (`internal/api/telegram_link.go`).

## 4. Модель данных

Миграции — `internal/store/migrations/*.sql`: партии, поставки, движения (`movements`), заказы и позиции,
корректировки, прыжки часов, пользователи/сессии/ключи, аудит, привязки Telegram, ручные правки горячих,
паузы блюд, состояние симулятора. Журнал движений — источник правды: остаток партии сходится с ним (инвариант 1).

## 5. Чем гарантируется корректность

`tests/invariants` — тринадцать сторожей, меняют только люди. Падение сторожа означает ошибку в коде, не в тесте.

| № | Инвариант |
|---|---|
| 1 | **Сохранение количества**: поступило − продано − списано + возвращено = `remaining`, `0 ≤ remaining ≤ quantity` |
| 2 | **Атомарность заказа**: заказ списывает всё или ничего |
| 3 | **Конкурентность заказов**: 50 горутин не продают одну порцию дважды |
| 4 | **Конкурентность с «дворником»**: просроченная партия не получает остаток обратно, без дедлоков |
| 5 | **FEFO**: порядок списания по `expires_at`, затем `id` |
| 6 | **Строгая граница срока**: доступна при `now < expires_at`, недоступна при `now ≥ expires_at` везде |
| 7 | **Конец дня**: «годен до D» — до начала D+1 по времени ресторана (в том числе при переходе на летнее время) |
| 8 | **Стоп-лист — функция остатков**: после любого события равен вычисленному заново |
| 9 | **Идемпотентность заказа**: повтор не списывает дважды, другое тело — `409` |
| 10 | **Горячие допустимы**: нет блюд из стоп-листа, каждая рекомендация ссылается на непросроченную партию |
| 11 | **Монотонность по сроку**: меньше времени до срока не понижает место блюда |
| 12 | **Арифметика количеств**: строгий разбор, переполнение и потеря точности — ошибка, а не число |
| 13 | **Время не идёт назад**: при смене скорости, прыжке, паузе и после рестарта |

Кроме сторожей: табличные тесты чистой логики (`internal/domain/*_test.go`), тесты хранилища на PostgreSQL,
HTTP-тесты роутера (в том числе права и негативные сценарии), сверка `docs/openapi.yaml` с реальным роутером
(`internal/api/openapi_test.go`), стабильность (`tests/stability`), пилот на 30 суток (`tests/pilot`), e2e на стенде.
CI: gofmt, `go vet`, `go test -race ./...` с БД, фронтенд (typecheck, vitest, сборка), контрастность и доступность.

## 6. Как прочитать код, если есть полчаса

1. `internal/domain/writeoff.go` — FEFO в 80 строках, самая важная функция.
2. `internal/store/orders.go` + `locks.go` — как заказ превращается в транзакцию.
3. `internal/domain/stoplist.go` — почему стоп-лист нигде не хранится.
4. `tests/invariants/inv03_concurrency_test.go` — как проверяется отсутствие двойной продажи.
5. `internal/api/ladder.go` — как несколько источников складываются в одну оценку в рублях.
6. `frontend/src/pages/today/` — экран «Сегодня»: деньги под риском и три блока действий.

## 7. Что сделано сознательно иначе, и что не сделано

- **Один ресторан — один экземпляр**: мультиарендности нет, сеть точек — через `cmd/hub`.
- **Интеграция с iiko проверена на эмуляторе** по публичной документации; боевой базы мы не видели
  (`docs/onboarding.md`, режим «тень»).
- **Эффект измерен в симуляторе** (`docs/bench.md`, `docs/pitch-numbers.md`): допущение «гость берёт предложенное
  блюдо в 30 % случаев» не измерено, проверяется на пилоте.
- **Заготовки/полуфабрикаты** (продление срока переработкой) показаны ступенью лестницы без расчёта — roadmap.
- **Помощник** отвечает по правилам, без модели: детерминированно и только по данным склада.
