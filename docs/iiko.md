# Адаптер iiko и эмулятор (`cmd/iiko-adapter`, `cmd/fake-iiko`)

SwapOwl — самостоятельная система; iiko — *пример* внешней учётной системы, для которой написан адаптер. **iikoServer API проверен на эмуляторе, не на живом iiko.** iiko переносит функционал в iikoCloud API; следующий адаптер будет под него (со слов эксперта «Флагмана»).

Сервер повторяет подмножество iikoServer API, чтобы адаптер (план 3.6) писался без доступа к настоящему iiko. Ядро сервиса фейк не знает и не вызывает. Типы формата — `internal/iiko/model.go`, сервер — `internal/iiko/fake`.

**Источники.** Пути и формы ответов взяты из публичной документации iiko (https://ru.iiko.help/articles/#!api-documentation/, https://api-ru.iiko.services/) по памяти автора; при подготовке задачи сверка со страницами документации не выполнялась (внешнего доступа не было), поэтому все детали формата следует считать требующими сверки. Отдельно помечено `[ПРЕДПОЛОЖЕНО]` то, чего в документации, по нашим сведениям, нет.

## Клиент настоящего сервера и сверка форматов (FS-115)

`internal/iiko/client` рассчитан на настоящий iikoServer:

- **Адрес и путь.** `-url https://host:443/resto` или `https://host:8080/resto`; если пути в адресе нет, берётся `Options.BasePath` (по умолчанию `/resto`). Константы путей в `internal/iiko` остаются с префиксом `/resto`, клиент подменяет его настроенным.
- **TLS.** Сертификат проверяется всегда; для самоподписанного — явный флаг (`Options.Insecure`, у `iiko-check` — `-insecure`). Таймаут запроса — `Options.Timeout` (60 с).
- **Сессия.** Лицензионных сессий у сервера мало: токен получается один раз и переиспользуется, при `401` клиент входит заново один раз (повторный `401` — ошибка), в конце вызывается `Logout`.
- **Повторы и частота.** `5xx` и сетевые ошибки повторяются (`Options.Retries`, по умолчанию 2, пауза `RetryPause` 1 с, удваивается); `4xx` не повторяются. `Options.MinInterval` — минимальная пауза между запросами (0 — без ограничения).
- **Записанные ответы** для тестов — `internal/iiko/client/testdata` (синтетические, без данных клиентов).

**Статус сверки: не выполнена.** В среде, где готовилась задача, нет доступа к `ru.iiko.help` (DNS не разрешается), поэтому ни один эндпоинт и поле не получили отметки «сверено (ссылка)»: все они остаются `[ПРЕДПОЛОЖЕНО]` до первого прогона `cmd/iiko-check` на настоящем сервере или чтения документации человеком. Что именно сверять в первую очередь (по памяти автора, не по документации):

| Что | Подозрение | Затрагивает |
|---|---|---|
| `products/list`: `mainUnit` | в настоящем iiko это, вероятно, GUID единицы измерения, а не «кг/л/шт»; нужен справочник единиц | fake, mapping |
| `products/list`: `shelfLifeHours` | поля в iiko нет (уже `[ПРЕДПОЛОЖЕНО]`) | fake, mapping |
| `logout` | в iiko, вероятно, `GET`; клиент шлёт `POST` как фейк | fake |
| `incomingInvoice`: формат `dateIncoming`, статусы, имена полей | не сверены | fake, mapping |
| `balance/stores`: имена полей, обязательные параметры (`department`/`store`) | не сверены | fake, mapping |
| стоп-лист | пути в iikoServer нет (уже `[ПРЕДПОЛОЖЕНО]`) | fake, adapter |

Расхождения, затрагивающие fake или mapping, не правятся в этом тикете: они переданы списком в комментарии к FS-115. Первая проверка на настоящем сервере — `iiko-check` (`docs/onboarding.md`, п. 3а): он показывает единицы, которые не распознаны, продукты без срока и поля, которых нет в ответе.

## Запуск

```
FAKE_IIKO_LOGIN=demo FAKE_IIKO_PASSWORD=demo go run ./cmd/fake-iiko -addr :8081 -seed 1 -origin 2026-01-01
```

Логин и пароль задаются флагами или переменными окружения; в коде их нет.

## Данные и время

- Справочники — `internal/seed`: 12 продуктов (`GOODS`) и 6 блюд (`DISH`). `id` = внешний id из сида (в настоящем iiko это GUID).
- Накладные и продажи — `internal/generator.Generate(seed, from, to)`. Часовой пояс — ресторана (Europe/Moscow).
- Сервер не вызывает `time.Now()`: время — параметры запроса (`from`/`to`/`timestamp`). Один интервал — не более 366 суток.
- Количества отдаются в основной единице продукта (г→кг, мл→л, шт→шт), как в iiko.

## Эндпоинты

Все, кроме `auth`, требуют `?key=<токен>`; без него или с чужим — `401`.

| Метод и путь | Назначение | Формат |
|---|---|---|
| `POST /resto/api/auth?login=&pass=` | токен; `pass` — SHA-1 пароля в hex | text/plain |
| `POST /resto/api/logout?key=` | выход (токен остаётся валидным) | text/plain |
| `GET /resto/api/v2/entities/products/list?key=` | номенклатура продуктов и блюд | JSON |
| `GET /resto/api/v2/assemblyCharts/getAll?key=` | техкарты (`dateFrom`/`dateTo` принимаются и игнорируются) | JSON |
| `GET /resto/api/documents/export/incomingInvoice?key=&from=yyyy-MM-dd&to=yyyy-MM-dd` | приходные накладные; `to` включительно | XML |
| `POST /resto/api/v2/reports/olap?key=` | продажи, `reportType=SALES` | JSON |
| `GET /resto/api/v2/reports/balance/stores?key=&timestamp=yyyy-MM-ddTHH:mm:ss[&product=]` | остатки на момент | JSON |
| `GET`/`POST /resto/api/v2/stopLists?key=` | чтение / замена стоп-листа | JSON |
| `POST /resto/api/documents/import/purchaseOrder?key=` | импорт документа «Заказ поставщику» [ПРЕДПОЛОЖЕНО]; тот же `id` заменяет документ | XML → `documentValidationResult` |
| `GET /resto/api/documents/export/purchaseOrder?key=[&id=]` | принятые заказы поставщику — для проверки в фейке [ПРЕДПОЛОЖЕНО] | XML |

OLAP: интервал `DateRange` — `To` **не входит** (в накладных `to` входит по дню). Фильтр `OpenDate.Typed` типа `DateRange` обязателен; группировки `DishId`, `DishName`, `OpenDate.Typed`; агрегаты `DishAmountInt`, `DishSumInt`. Прочие поля — `400`.

## [ПРЕДПОЛОЖЕНО]

- **Стоп-лист.** В iikoServer записи стоп-листа не нашлось (стоп-листы — в iikoCloud `/api/1/stop_lists`, с организациями и терминальными группами). Фейк даёт простой путь `/resto/api/v2/stopLists` с телом `{"items":[{"productId","balance"}]}`; `POST` заменяет список целиком, id проверяются по справочнику. Реальный путь и форма для подключения — уточнить.
- **Срок годности.** В iiko партионных сроков нет (`solution.md`, 8.3 п. 3). Фейк добавляет в продукт нестандартное поле `shelfLifeHours` из сида, иначе адаптеру нечего подставить в `expires_at`.
- **Остатки.** `balance` считает историю от `-origin`, а интервал ограничен 366 сутками: при `timestamp` позже origin+366 суток ответ `400` — сдвигайте `-origin`. Остаток = приход − расход по техкартам с `-origin` до `timestamp`, не ниже нуля после каждого расхода (дефицит не «съедает» будущие поставки); сроки годности не учитываются. Склад один (`main-store`), поставщик один (`supplier-1`).
- **Продажи.** Только OLAP по заказам из генератора; выгрузка заказов (`/api/1/deliveries`, `orders`) не реализована. Цена продажи = цена блюда из сида.
- **Накладные.** Состав полей `document` сокращён (id, номер, дата, статус, поставщик, склад, позиции `product/amount/price/sum`). Цена — по сидовой цене продукта.
- **Заказ поставщику.** Путь импорта `documents/import/purchaseOrder`, поля документа (по образцу приходной накладной: `id`, `documentNumber`, `dateIncoming`, `supplier`, `defaultStore`, `items/item{num,product,amount}`) и ответ `documentValidationResult` по документации iikoServer не сверены — `docs/iiko-real.md` (FS-115) в репозитории нет. `GET export/purchaseOrder` есть только у фейка. Что в реальном iiko повторный импорт с тем же `id` обновляет документ, а не создаёт второй, — тоже допущение; от дубля нас защищает и `id`-идемпотентность на нашей стороне (один заказ — одна строка outbox).
- **Токен.** Детерминированный (из seed, логина и пароля), не истекает; в настоящем iiko токен привязан к лицензии и сессии.
- **Техкарты.** Одна на блюдо, без потерь при обработке (`amountIn=amountMiddle=amountOut`).

# Адаптер (`cmd/iiko-adapter`)

Отдельный процесс: ходит в iiko (сейчас — `cmd/fake-iiko`) и в наш API по ключу `Authorization: Bearer`; о БД ничего не знает (`.ai/solution.md`, 8.0–8.2). Клиент iiko — `internal/iiko/client`, переводы полей — `internal/iiko/mapping`.

## Запуск

```
IIKO_URL=http://localhost:8081 IIKO_LOGIN=demo IIKO_PASSWORD=demo \
API_URL=http://localhost:8080 API_KEY=<ключ operator или admin> \
go run ./cmd/iiko-adapter          # цикл; флаг -once — один проход
```

Один проход: справочники → накладные → продажи → исходящие сообщения (стоп-лист, см. «Стоп-лист через outbox»). Сбой этапа не останавливает остальные; процесс повторяет проход через `ADAPTER_INTERVAL`.

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `IIKO_URL`, `IIKO_LOGIN`, `IIKO_PASSWORD` | — (обязательны) | доступ к iiko |
| `API_URL`, `API_KEY` | — (обязательны) | наш API и ключ; `PUT /api/catalog` требует `admin` или ключ `operator` |
| `ADAPTER_STATE_FILE` | `iiko-adapter-state.json` | файл курсоров |
| `ADAPTER_INTERVAL` | `5m` | пауза между проходами |

| `ADAPTER_START_DATE` | вчера | `yyyy-MM-dd`, с какого дня читать при пустом курсоре |
| `ADAPTER_DEFAULT_PRICE_MINOR_PER_1000` | `10000` | цена продукта, если в накладных за 30 дней её нет |
| `ADAPTER_DEFAULT_LEAD_DAYS` | `2` | срок поставки продукта |
| `ADAPTER_DEFAULT_PACK_SIZE` | `1000` | кратность заказа поставщику |
| `ADAPTER_DEFAULT_PRIOR_DAILY` | `10` | априорный дневной спрос блюда |

| `ADAPTER_SUPPLIER_ID`, `ADAPTER_STORE_ID` | — | id поставщика и склада документа «Заказ поставщику»; в боевом режиме без них доставка заказа — ошибка с понятным текстом |
| `ADAPTER_SHADOW_FILE` | `iiko-adapter-shadow.json` | журнал теневого режима («что было бы отправлено») |

## Соответствие полей

| iiko | Наш API |
|---|---|
| `products/list`, `type=GOODS` → `id`, `name`, `mainUnit` (кг/л/шт), `shelfLifeHours` | `PUT /api/catalog` `products[]`: `id`, `name`, `unit` (g/ml/pcs), `shelf_life_hours` |
| цена продукта: последняя `price` позиции накладной за 30 дней (руб за основную единицу) | `price_minor_per_1000` = цена·100·1000 / (1000 для кг/л, 1 для шт) |
| `type=DISH` → `id`, `name`, `defaultSalePrice` | `dishes[]`: `id`, `name`, `price_minor` (копейки) |
| действующая техкарта (`dateTo=null`): `items[].productId`, `amountIn` / `assembledAmount` | `recipe[]`: `product_id`, `quantity` (целое число базовых единиц, не меньше 1), `unit` (g/ml/pcs) |
| приходная накладная (`status=PROCESSED`): `id`, `documentNumber`, `dateIncoming`, `items[]` | `POST /api/deliveries`: `id` (= id накладной), `number`, `created_at` и `occurred_at` (оба = `dateIncoming` в часовом поясе ресторана), `items[]`: `product_id`, `quantity` (целые базовые единицы), `unit` (g/ml/pcs), `shelf_life_hours` |
| OLAP `SALES`: `DishId`, `UniqOrderId.Id` (чек), `CloseTime` (время закрытия чека), `DishAmountInt` | `POST /api/orders`, `source: "pos"`: один заказ на чек, `items[]`: `dish_id`, `portions`; `occurred_at` = `CloseTime` (часовой пояс ресторана); `id` = UUID v5 от `iiko-check:<id чека>`. Если в выгрузке нет id чека — один заказ на строку, `id` = UUID v5 от `iiko-line:<дата>\|<время>\|<блюдо>`; нет времени — `occurred_at` не передаётся (время приёма) |
| `GET /api/outbox`, `kind=stoplist`: `payload` — блюда с `available=false` | `POST stopLists`: `items[]`: `productId` = id блюда, `balance` = 0 (заменяет список целиком, только при изменении) |

Не передаются: удалённые позиции, блюда без действующей техкарты или с неизвестным продуктом в ней, накладные не в статусе `PROCESSED`, позиции с неизвестным продуктом (всё это — строкой в журнале).

## Курсоры и повторы

Курсоры — даты `yyyy-MM-dd` в файле состояния: `invoices` (последний прочитанный день; сегодняшний день читается заново) и `sales` (первый день, продажи которого читаются заново; это сегодняшний день, пока он не закрыт). Продажи читаются и за сегодня: API принимает события не старше `LATE_EVENTS_HOURS`, ждать конца дня нельзя. Чек, принятый раньше, приходит повторно с тем же id (`200`). Курсор двигается после успешной передачи; повтор после сбоя безопасен: поставка с тем же id и заказ с тем же id принимаются API повторно (`200`). Ответ `4xx` (кроме 401, 403, 429), например `409` при том же id и другом содержимом или `400` на невалидную позицию, пишется в журнал, элемент пропускается, курсор идёт дальше; сеть и `5xx` останавливают проход, повтор на следующем. Событие старше окна `LATE_EVENTS_HOURS` (`400` с полем `occurred_at`) повтором не исправить: адаптер пишет его в журнал и в счётчик (строка «старше окна опоздания … всего за запуск: N», каждый id считается один раз) и идёт дальше; такие продажи вносятся корректировкой. Продажи блюд, которых нет в принятом каталоге, пропускаются с записью в журнал. Если каталог в этом проходе не принят, накладные и продажи не передаются, курсоры стоят на месте.

## Допущения

- Чек и время продажи берутся из OLAP-полей `UniqOrderId.Id` и `CloseTime` (строка `yyyy-MM-ddTHH:mm:ss`, часовой пояс ресторана) [ПРЕДПОЛОЖЕНО: форма значения `CloseTime` в боевом iiko сверяется при подключении]. Фейк отдаёт оба поля.
- Время события (`.ai/solution.md`, 2.4а): накладная — `dateIncoming`, продажа — `CloseTime`: чек появляется в OLAP и списывается в iiko при закрытии, а время открытия у долгого чека может не уложиться в окно опоздания. Срок партии считается от даты накладной, а не от приёма.
- `lead_days`, `pack_size`, `prior_daily` в iiko нет — берутся из переменных `ADAPTER_DEFAULT_*`; каждый проход обновляет каталог (в том числе цены) теми же правилами.
- Стоп-лист в iiko — `[ПРЕДПОЛОЖЕНО]` (см. выше); блюда передаются как `productId`.
- Ack API принимает только `{ok, error?}`, поля для пометки `shadow` в нём нет. Поэтому в теневом режиме строка outbox подтверждается обычным `ok`, а пометка живёт в локальном журнале адаптера (`ADAPTER_SHADOW_FILE`). Следствие: после перехода в бой старые сообщения заново не придут.

## Сверка остатков (`iiko-adapter reconcile`)

Теневой режим (`.ai/solution.md`, 8.4): остатки склада из iiko (`reports/balance/stores` на текущий момент) против нашего `GET /api/products` (непросроченные партии). Переменные те же, что у адаптера. Только чтение с обеих сторон, ничего не корректируется.

```
iiko-adapter reconcile [-json] [-all]
```

Столбцы: продукт, у нас, в iiko, разница (у нас − iiko, базовые единицы g/ml/pcs), разница в рублях. По умолчанию — только продукты с расхождением; `-all` — все; `-json` — массив `{product_id, name, unit, ours, iiko, diff, diff_minor}` (`diff_minor` — копейки).

Допущения: цена для рублей — `Sum/Amount` остатка iiko, а при нулевом остатке — цена последней накладной за 30 дней (нет цены — 0). Остаток iiko не учитывает сроки годности, а наш — учитывает: продукт с просроченной партией покажет расхождение, это ожидаемо.

## Стоп-лист через outbox

Стоп-лист адаптер берёт из `GET /api/outbox` (опроса `/api/stop-list` больше нет). Сообщение `kind=stoplist` несёт стоп-лист целиком, поэтому из накопившихся сообщений в iiko уходит последнее, а все прочитанные подтверждаются.

- **Доставлено** — `POST /api/outbox/{id}/ack {"ok":true}`.
- **Ошибка iiko** — `ack {"ok":false,"error":"…"}` (на стороне API растёт `attempts`, видно в метриках) и повтор с нарастающей паузой: `ADAPTER_RETRY_BASE`, ×2 после каждой неудачи, не больше `ADAPTER_RETRY_MAX`. Пауза хранится в памяти процесса.
- **При старте** первый проход читает всё недоставленное с прошлого раза: очередь на стороне API, курсора у адаптера для неё нет.
- Сообщения других видов (кроме `supply_order`, см. ниже) адаптер не трогает и пишет о них в журнал.

## Заказ поставщику через outbox (FS-121)

Экран «Поставки»: выбранные строки предложения → «Отправить заказ в iiko» → `POST /api/supply-orders {id, items:[{product_id, qty}]}` (`qty` — целое в базовой единице продукта). Сервер той же транзакцией кладёт в outbox сообщение `kind=supply_order` (новое значение в существующей колонке, миграции нет); идемпотентность — по `id` в payload под advisory-блокировкой: повтор того же состава — тот же заказ (`200`, `replayed`), другой состав — `409 order_conflict`.

- **Боевой режим:** адаптер собирает документ «Заказ поставщику» (`id` документа = `id` заказа; г и мл переводятся в кг и л) и импортирует его в iiko, затем `ack ok`. Потерянный ack ведёт к повторной доставке того же `id` — документ заменяется, дубля нет.
- **Теневой режим:** в iiko ничего не уходит; в журнал адаптера пишется «заказ поставщику не отправлен в iiko, отправил бы: …», сообщение подтверждается. Статус заказа на экране при этом станет «доставлен в iiko» — подтверждение outbox, а не факт записи в iiko; отличить теневой режим можно только по журналу адаптера (допущение, см. PR).
- **Ошибка iiko:** `ack {ok:false}`, повтор с паузой как у стоп-листа; заказы независимы друг от друга и от стоп-листа.
- **Статус на экране** (`GET /api/supply-orders/{id}`, опрос раз в 3 с до доставки): «отправлен» — в очереди, «доставлен в iiko» — `delivered_at` проставлен, «ошибка доставки» — была неудачная попытка, адаптер повторит.

## Теневой и боевой режим (`ADAPTER_MODE`)

`shadow` (по умолчанию): в iiko ничего не пишется. Справочники, накладные и продажи по-прежнему идут из iiko в наш API (это чтение iiko). Сообщение outbox подтверждается как доставленное, а то, что ушло бы в iiko, пишется в журнал `ADAPTER_SHADOW_FILE` (хранится 60 дней). `live`: стоп-лист отправляется в iiko.

### Отчёт за день

```
iiko-adapter shadow-report [-json] [-all] [-date yyyy-MM-dd]
```

Таблица или JSON `{date, mode, events[], final_stoplist[], reconcile[]}`: события стоп-листа за день (время, строка outbox, число позиций, что добавлено и убрано относительно предыдущего события, `superseded` — сколько накопившихся сообщений вытеснено) и итоговый стоп-лист на конец дня, затем сверка остатков с iiko (`reconcile`, без `-all` — только расхождения). Только чтение.

### Порядок перехода из тени в бой

1. Запустить адаптер в `shadow` (значение по умолчанию) на реальном iiko и держать 1–2 недели (`.ai/solution.md`, 8.4).
2. Каждый день запускать `shadow-report`. Проверять: в `reconcile` нет необъяснённых расхождений (просроченные партии — ожидаемое, см. выше), а «что было бы отправлено» совпадает с тем, что повара видят в нашем стоп-листе.
3. Сверить с iiko вручную формат записи стоп-листа: путь и тело `[ПРЕДПОЛОЖЕНО]` (см. выше) в настоящем iiko не проверены. До этой проверки в `live` не переходить.
4. Согласовать с рестораном окно переключения, снять копию файла состояния и журнала.
5. Выставить `ADAPTER_MODE=live` и перезапустить адаптер: первый проход отправит текущий стоп-лист: в тени сообщения уже подтверждены и очередь пуста, поэтому в боевом режиме адаптер один раз за запуск, если очередь пуста, читает `GET /api/stop-list` и записывает его в iiko (без изменений — не пишет). Дальше стоп-лист идёт из outbox.
6. В первый час сверить стоп-лист в iiko с нашим; ошибки доставки видны в журнале адаптера и в метрике недоставленных исходящих.
7. Откат: `ADAPTER_MODE=shadow` и перезапуск; уже отправленное в iiko остаётся, его снимает ресторан вручную.
