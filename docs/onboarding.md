# Регламент подключения ресторана (iiko)

Для инженера внедрения. Источник: `.ai/solution.md`, 8.0, 8.3, 8.4. Позиционирование: наш сервис — надстройка над iiko, не замена; iiko остаётся учётной системой. Один ресторан — один экземпляр сервиса со своим конфигом, мультиарендности нет.

Состояние на момент написания: адаптер `cmd/iiko-adapter` проверен только против фейкового iiko (`cmd/fake-iiko`); эндпоинты накладных и стоп-листа iiko по официальной документации не сверены (`docs/iiko.md`, раздел `[ПРЕДПОЛОЖЕНО]`). **Что из описанного ниже ещё не реализовано, помечено «НЕТ В КОДЕ».**

Цикл: анкета → экземпляр и ключ → справочники → начальные остатки → теневой режим 1–2 недели → боевой режим. До закрытия пунктов 1–7 из 8.3 система остаётся демонстрацией на данных клиента, решений по ней ресторан принимать не должен.

## 1. Анкета ресторана

Заполняется до любых работ. Без ответов на первые четыре пункта дальше не идти.

| Вопрос | Зачем |
|---|---|
| Версия iiko (Server/RMS/Cloud), адрес сервера, откуда он доступен | адаптер ходит в `IIKO_URL` по сети |
| Выдан ли отдельный пользователь iiko для интеграции (логин/пароль), права на чтение номенклатуры, техкарт, накладных, OLAP-продаж, остатков; на запись стоп-листа | `IIKO_LOGIN`, `IIKO_PASSWORD` |
| Реальные пути накладных и стоп-листа в этой версии iiko | в фейке они `[ПРЕДПОЛОЖЕНО]`; если не совпадают — нужна доработка адаптера до подключения |
| Один склад или несколько; как заведены поставщики | адаптер читает накладные без разбора складов |
| Источник сроков годности: в iiko партионных сроков нет | срок задаётся при приёмке или по умолчанию в продукте (п. 3) |
| Часы работы, в том числе через полночь и по дням недели | `OPEN_AT`/`CLOSE_AT` — одно окно на все дни (пробел 8, ниже) |
| Часовой пояс | `RESTAURANT_TZ`, `ADAPTER_TZ` |
| Полуфабрикаты, потери при обработке, упаковки с весовыми рецептами | не поддержаны (пробел 9) |
| Кто принимает решения по стоп-листу и кто видит предупреждения | роли и ключи |

## 2. Экземпляр, доступ и ключ интеграции

1. Развернуть экземпляр (`deploy/docker-compose.yml`, `.env` по образцу): `DEMO_MODE=false`, `CLOCK_MODE=real`, `SEED_ON_EMPTY=false`, `AUTH_REQUIRED=true`, `DATABASE_URL`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `RESTAURANT_TZ`, `OPEN_AT`, `CLOSE_AT`. Сервис стартует с пустыми справочниками; `/api/demo/*` отвечают `404`. Пароль PostgreSQL обязателен. Подробности — README, «Экземпляр для ресторана».
2. Войти под `ADMIN_LOGIN` (`POST /api/auth/login`), создать пользователей управляющих (`POST /api/users`, роли `viewer`/`operator`/`admin`).
3. Выпустить ключ интеграции: `POST /api/api-keys` `{"name":"iiko-adapter","role":"operator"}`. Роль `admin` для ключа недопустима, нужна `operator`: `PUT /api/catalog` принимает `admin` или ключ `operator`. Ключ показывается один раз — сохранить в менеджере секретов, не в репозитории и не в тикете. Это `API_KEY` адаптера.
4. Проверить: `GET /healthz` отвечает, `GET /api/stop-list` с ключом отдаёт пустой список.

Скрипта «новый ресторан» (экземпляр + ключ + конфиг одной командой, 8.0а) **НЕТ В КОДЕ** — шаги выполняются вручную.

## 3. Запуск адаптера и справочники

Переменные (полный список — `docs/iiko.md`): обязательны `IIKO_URL`, `IIKO_LOGIN`, `IIKO_PASSWORD`, `API_URL`, `API_KEY`. Задать явно: `ADAPTER_TZ`, `ADAPTER_STATE_FILE` (путь на постоянном томе, иначе курсоры потеряются), `ADAPTER_START_DATE`.

Значения `ADAPTER_DEFAULT_PRICE_MINOR_PER_1000`, `ADAPTER_DEFAULT_LEAD_DAYS`, `ADAPTER_DEFAULT_PACK_SIZE`, `ADAPTER_DEFAULT_PRIOR_DAILY` — заглушки: срок поставки, кратность заказа и априорный спрос в iiko нет. Согласовать их с управляющим, иначе предложение поставок и горячие предложения будут считаться по цифрам из заглушек.

Порядок:
1. Пробный прогон каталога без записи: `PUT /api/catalog?dry_run=true` покажет, что изменится.
2. Первый проход вручную: `go run ./cmd/iiko-adapter -once`. Проход делает: справочники → накладные → продажи → исходящие сообщения (стоп-лист из outbox). Если каталог не принят, накладные и продажи не передаются, курсоры стоят.
3. Прочитать журнал прохода: пропущенные блюда без действующей техкарты, позиции с неизвестным продуктом, накладные не в `PROCESSED` — это строки в журнале. Каждую пропущенную позицию обсудить с рестораном: иначе блюдо не попадёт в стоп-лист.
4. Срок годности: в iiko его нет. Задать срок хранения по умолчанию у продуктов (`shelf_life_hours` в каталоге) и проверить, что у каждого скоропортящегося продукта он задан и осмыслен; без него партии получат неверный `expires_at`, а все решения по срокам будут ложными.
5. Сверить 5–10 блюд вручную: рецепт в нашей системе равен техкарте в iiko, единицы (г/мл/шт) совпадают.

Смена единицы у существующего продукта отвергается (`409`), удаление продукта с партиями — отдельное решение (пробел 5).

## 3а. Проверка подключения к iiko (первая команда у клиента)

Только чтение: логин, номенклатура, техкарты, накладные и продажи за последние 7 дней, остатки на сейчас, `logout`. Ничего в iiko не пишет.

```
go run ./cmd/iiko-check -url https://host:443/resto -login <логин> -password <пароль>
```

Флаги и переменные: `-url`/`IIKO_URL`, `-login`/`IIKO_LOGIN`, `-password`/`IIKO_PASSWORD`; `-base-path` (если пути `/resto` нет в `-url`), `-insecure` (самоподписанный сертификат), `-timeout`, `-rate` (пауза между запросами), `-tz`. Код выхода: `0` — всё прочитано, `1` — сбой (раздел отчёта помечен «ОШИБКА»), `2` — неверные флаги.

Отчёт: сколько продуктов, блюд и техкарт; какие единицы измерения не распознаны (такие продукты адаптер пропустит); у скольких продуктов нет срока хранения; поля, которых нет в ответе или которые не разобрались. Любой раздел «ОШИБКА» или непустой список полей — повод сверить формат с документацией до запуска адаптера (`docs/iiko.md`, «Клиент настоящего сервера»). Проверка против фейка: `go run ./cmd/fake-iiko -login demo -pass demo` и `iiko-check -url http://127.0.0.1:8081 -login demo -password demo`.

## 4. Начальные остатки — поставкой-инвентаризацией

Корректировки остатка (инвентаризация как вид движения) **НЕТ В КОДЕ** (пробел 4), поэтому начальный остаток вносится обычной поставкой.

1. Провести физическую инвентаризацию склада в момент, когда движения остановлены (закрытая смена). По каждой позиции: продукт, количество, срок годности каждой партии.
2. Отправить одну или несколько поставок `POST /api/deliveries` с id вида `inventory-<yyyy-MM-dd>-<склад>`, `number` аналогично, позиции — по партиям с явными `unit`, `quantity` и сроком (`shelf_life_hours` или абсолютная дата). Повтор того же id безопасен и остатки не удваивает.
3. Известное искажение: время события равно времени приёма (пробел 1). Поставка получит `received_at` = момент отправки, а `expires_at` для длительности хранения считается от него. Поэтому для партий с известной датой годности передавать абсолютную дату, а не длительность.
4. Закрыть окно: адаптер при первом проходе читает накладные с `ADAPTER_START_DATE`. Если ранее начавшиеся накладные уже учтены остатком из инвентаризации, `ADAPTER_START_DATE` ставится на дату инвентаризации, иначе остатки задвоятся.
5. Сверить остаток по 10 ключевым продуктам с остатком в iiko на тот же момент (`GET /resto/api/v2/reports/balance/stores`).

## 5. Теневой режим (1–2 недели) со сверкой

Цель: убедиться, что наш стоп-лист и остатки согласуются с iiko, не трогая стоп-лист кассы.

**Режим.** `ADAPTER_MODE=shadow` (по умолчанию): в iiko ничего не пишется, outbox подтверждается, а то, что ушло бы в iiko, попадает в журнал адаптера. Ежедневный отчёт — `iiko-adapter shadow-report` (события стоп-листа за день, итоговый стоп-лист и сверка остатков `reconcile`); порядок перехода в бой — `docs/iiko.md`, «Теневой и боевой режим».

- Пока пути стоп-листа в боевой версии iiko не сверены с документацией (`[ПРЕДПОЛОЖЕНО]` в `docs/iiko.md`), в `live` не переходить.
- Ежедневно разбирать отчёт; к боевому режиму допускать, когда расхождения за 7 подряд дней объяснены и не растут.

Типовые причины расхождений: пропущенные блюда/позиции (журнал п. 3), срок годности по умолчанию, продажа блюда, которого нет в каталоге, ручные списания и корректировки в iiko, не попавшие к нам (пробел 4), события задним числом (пробел 1).

Продажи передаются только за закрытые дни, сводным заказом за день (`source: "pos"`, id — UUID v5 от `iiko-sales:<yyyy-MM-dd>`), без чеков: недостача при списании записывается расхождением, а не отказом.

## 6. Переход в боевой режим

Условия: теневой период пройден, расхождения объяснены, срок годности и заглушки `ADAPTER_DEFAULT_*` согласованы, пути стоп-листа в боевой версии iiko сверены с документацией.

1. Зафиксировать на бумаге у ресторана, что стоп-лист в iiko ведёт сервис, и кто отвечает за ручное снятие позиции.
2. Включить `ADAPTER_MODE=live` и перезапустить адаптер.
3. Первый боевой проход выполнить `-once` при инженере; проверить в iiko, что стоп-лист появился и совпадает с `GET /api/stop-list`. Обычный цикл читает стоп-лист из `GET /api/outbox`. Стоп-лист заменяется целиком и только при изменении.
4. Запустить цикл (`ADAPTER_INTERVAL`, по умолчанию 5 мин), следить за журналом первые сутки.
5. Откат: остановить адаптер и вручную очистить/восстановить стоп-лист в iiko. Очередь исходящих сообщений (outbox) хранит недоставленное: если iiko был недоступен, адаптер повторяет отправку с нарастающей паузой, а при перезапуске дочитывает очередь. Откат в `shadow` перестаёт отправлять, уже отправленное в iiko остаётся.

## 7. Известные пробелы (8.3) — как есть, без обещаний

Отмечено по состоянию репозитория на момент написания (проверено по коду, не по плану).

| № | Пробел | Состояние |
|---|---|---|
| 1 | Время события = время приёма; история пакетом даёт ложные отказы и завышенный срок | **Открыт** |
| 2 | Заказ от внешней кассы: списать доступное, недостачу записать расхождением | **Закрыт** — `source: "pos"` |
| 3 | Источник сроков годности | **Частично**: срок по умолчанию в продукте (`PUT /api/catalog`) и срок позиции при приёмке; в iiko партионных сроков по-прежнему нет, значения вводит человек |
| 4 | Корректировка остатка (инвентаризация, брак, возврат, отмена) | **Открыт**; обход — п. 4 |
| 5 | Загрузка справочников с пробным прогоном | **Закрыт** — `PUT /api/catalog`, `dry_run`. Правила смены единицы — `409`; остальные граничные случаи (удаление продукта с партиями) не описаны |
| 6 | Доступ: смена пароля самим пользователем, счётчик входов в БД, журнал действий в БД | **Открыт** (смены пароля и журнала в БД нет) |
| 7 | Обратная связь в кассу с журналом доставки и повторами | **Частично**: адаптер отправляет стоп-лист; очереди `outbox`, подтверждений и метрик нет |
| 8 | Расписание: через полночь, по дням недели | **Открыт** |
| 9 | Рецепты: полуфабрикаты, потери, упаковки | **Открыт**; в адаптере техкарта без потерь |
| 10 | Эксплуатация: резервные копии с проверкой, метрики, оповещения, обновление многих экземпляров | **Открыт** |
| 11 | Адаптер под самую частую систему | Есть для iiko, только против фейка; на живом iiko не проверялся |

Прогон перед пилотом (30 симулированных дней через адаптер на фейковом iiko, 8.0а) на момент написания не выполнялся.

## 8. Чек-лист передачи ресторану

- [ ] Анкета заполнена, пути iiko сверены.
- [ ] Ключ `operator` выпущен, хранится в менеджере секретов.
- [ ] Каталог загружен, пропуски из журнала разобраны.
- [ ] Срока годности нет ни у одного скоропортящегося продукта без значения по умолчанию.
- [ ] Начальные остатки внесены поставкой-инвентаризацией и сверены с iiko.
- [ ] Теневой период пройден (после реализации режима) и расхождения объяснены.
- [ ] Ресторан знает, что система пока демонстрационная по пробелам 1, 4 и 6 и как вручную снять позицию стоп-листа.
