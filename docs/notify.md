# Уведомления управляющему в Telegram

Отдельный процесс `cmd/notifier`, как адаптер: о БД ничего не знает, ходит в наш API по ключу `viewer`
и слушает `GET /events`.

## Что присылает

- **`batch.expiring`** — сообщение: продукт, партия, количество под угрозой, когда истекает, сколько это в рублях,
  какие блюда продвигать (из `/api/hot-offers`, где в `reasons` есть эта партия). На одну партию — одно сообщение
  за жизнь процесса; если партии уже нет в `/api/alerts`, сообщение не шлётся.
- **Дневная сводка** — раз в день в `NOTIFY_DIGEST_AT` по времени ресторана (`timezone` и `now` из `GET /api/clock`):
  списано за день в рублях (`/api/analytics/writeoffs`), под риском (`/api/alerts`, без просроченных),
  расхождения кассы (`/api/analytics/shortfalls`). Если процесс стартовал после этого времени, за сегодня сводки не будет.

## Команды и кнопки (long polling `getUpdates`)

Бот принимает апдейты только из чата `NOTIFY_TG_CHAT` (или `TELEGRAM_CHAT_ID`); чужие чаты игнорируются, факт пишется в журнал.

| Команда | Ответ |
|---|---|
| `/hot` | топ-3 горячих предложения: цель в порциях и партия |
| `/stop` | стоп-лист с причинами (чего и сколько не хватает) |
| `/expiring` | что истекает сегодня (по времени ресторана) с суммой в ₽ |
| `/summary` | дневная сводка по запросу (как вечерняя) |

**Партия без подтверждённого срока (2.1а).** На событие `delivery.accepted` (и при проходе каждые 30 с) для партий из
`GET /api/receiving` приходит сообщение с кнопками:

- **Подтвердить срок** — `PATCH /api/batches/{id}/expiry` с `shelf_life_hours` = текущий срок партии (тот же маршрут, что у экрана «Приёмка»).
- **Изменить срок** — бот просит ответ: целое число часов от приёмки или дату `ДД.ММ.ГГГГ` / `ГГГГ-ММ-ДД` (конец дня).

Повторное нажатие (дубли Telegram) безопасно: нажатия дедуплицируются по id, а партия, которой уже нет в `/api/receiving`,
получает ответ «уже подтверждено», без вызова `PATCH`. После рестарта уже существующие неподтверждённые партии не рассылаются повторно.

## Права ключа

Читает бот ключом `API_KEY` (`viewer`). Менять срок можно только ключом `API_KEY_OPERATOR` — отдельный ключ с именем `notifier`
и ролью `operator` (или `admin`); подтверждение попадает в журнал действий как `batch_expiry_confirmed` от этого ключа.
Бот перед записью проверяет роль через `GET /api/auth/me`. Если ключа нет, роль ниже `operator`, ответ `401/403` или нет маршрута
(`404`) — API не трогается, в чат приходит просьба завести тикет на выдачу прав. Без `API_KEY_OPERATOR` сообщения с кнопками не отправляются.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `API_URL`, `API_KEY` | адрес API и ключ роли `viewer` |
| `API_KEY_OPERATOR` | необязательно: ключ `notifier` с ролью `operator`, нужен для кнопок |
| `TELEGRAM_BOT_TOKEN`, `NOTIFY_TG_CHAT` (или `TELEGRAM_CHAT_ID`) | бот и чат; в журнал не попадают (ошибки очищаются от токена) |
| `NOTIFY_DIGEST_AT` | `ЧЧ:ММ`, по умолчанию `22:00` |
| `TELEGRAM_API_URL` | необязательно: заменить `https://api.telegram.org` (тесты, прокси) |

## Известные ограничения

- В API нет чтения цен, поэтому рубли по партии оцениваются по цене за единицу из потерь продукта за последние 30 дней
  (списания, затем расхождения кассы). Нет потерь — в сообщении «нет данных о цене», в сводке такая партия считается отдельно.
- Дедупликация сообщений — в памяти процесса. При старте уже истекающие партии помечаются отправленными без сообщений (перезапуск не заваливает чат).
  но и повторно на уже отправленные событие не придёт.
- `batch.expiring` приходит один раз, поэтому упавшая отправка и разрыв SSE догоняются проходом по `/api/alerts` (каждые 30 с и после переподключения).
