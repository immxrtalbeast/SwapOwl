# Уведомления управляющему в Telegram

Отдельный процесс `cmd/notifier`, как адаптер: о БД ничего не знает, ходит в наш API по ключу `viewer`
и слушает `GET /events`.

## Что присылает

- **`batch.expiring`** — сообщение: продукт, партия, количество под угрозой, когда истекает, сколько это в рублях,
  какие блюда продвигать (из `/api/hot-offers`, где в `reasons` есть эта партия). На одну партию — одно сообщение
  за жизнь процесса; если партии уже нет в `/api/alerts`, сообщение не шлётся.
- **Дневная сводка** — раз в день в `NOTIFY_DIGEST_AT` по времени ресторана (`timezone` и `now` из `GET /api/clock`):
  списано за день в рублях (`/api/analytics/writeoffs`), под риском (`/api/alerts`, без просроченных),
  расхождения кассы (`/api/analytics/shortfalls`). Если процесс стартовал после этого времени, за сегодня сводки не будет.

## Недельный отчёт собственнику

По понедельникам в `NOTIFY_WEEKLY_AT` (по умолчанию `09:00`, время ресторана из `GET /api/clock` — на стенде
срабатывает и от прыжка часов) в чат `NOTIFY_OWNER_CHAT` (отдельно от чата управляющего) уходит PNG-картинка
(крупная сумма в ₽ и столбики по дням, рисуется на Go без внешних сервисов) с подписью: списано за 7 суток,
топ-3 продукта по потерям, списания по дням эмодзи-столбиками, ссылка `NOTIFY_STAND_URL`. Если картинку отправить не
удалось — уходит текст. Без `NOTIFY_OWNER_CHAT` рассылка выключена (команда `/week` работает). Если процесс стартовал
после времени отчёта, за этот понедельник отчёта не будет.

- «Под угрозой на следующей неделе» берётся из `GET /api/forecast/writeoffs` (ожидаемый формат — как у
  `/api/analytics/writeoffs`: `total_minor`). Пока маршрута нет (404) — строка пропускается.
- Число порций, проданных по горячим предложениям, API не отдаёт — в отчёте не показывается.

## Команды и кнопки (из чата управляющего)

Бот читает обновления long polling'ом (`getUpdates`, вебхук не нужен). Принимаются только сообщения и нажатия
из чата `NOTIFY_TG_CHAT` (он же `TELEGRAM_CHAT_ID`); чужие чаты игнорируются, в журнал пишется только id чата.

| Команда | Ответ |
|---|---|
| `/hot` | топ-3 горячих предложения: блюдо, цель в порциях, партия (`/api/hot-offers`) |
| `/stop` | стоп-лист с причинами: чего и сколько не хватает (`/api/stop-list`) |
| `/expiring` | истекающее сегодня (по времени ресторана) с суммой в ₽ (`/api/alerts`) |
| `/summary` | дневная сводка по запросу (как ежедневная) |
| `/week` | недельный отчёт (см. ниже) в чат, откуда пришла команда |

**Партия пришла без срока** (`delivery.accepted` и проход каждые 30 с по `GET /api/receiving`, партии с
`expiry_source = product_default`): сообщение с кнопками.
- «Подтвердить срок» — `PATCH /api/batches/{id}/expiry` с `shelf_life_hours`, равным текущему сроку (округлённому до часа);
- «Изменить срок» — бот просит ответить числом часов от приёмки или датой `ДД.ММ.ГГГГ`, затем тот же `PATCH`.

Это тот же маршрут, что у экрана «Приёмка». Повторное нажатие (дубль от Telegram): партии уже нет в
`/api/receiving` — ответ «уже подтверждён», API не вызывается. В журнале действий (`GET /api/audit`) подтверждение
записано от ключа `notifier`; кто именно нажал кнопку в Telegram, API не получает.

## Права ключа

Чтение — `viewer`. Для кнопок нужна роль **`operator`** (`PATCH /api/batches/{id}/expiry`). Если у ключа
нет прав (401/403/405) или маршрута нет (404) — бот ничего больше не вызывает и отвечает в чат, что нужно
передать в тикет; повторять запрос нет смысла. Без `operator` команды `/hot`, `/stop`, `/expiring`, `/summary` работают.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `API_URL`, `API_KEY` | адрес API и ключ роли `operator` (для кнопок; для чтения достаточно `viewer`) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (или `NOTIFY_TG_CHAT`) | бот и числовой id чата; в журнал не попадают (ошибки очищаются от токена) |
| `NOTIFY_OWNER_CHAT`, `NOTIFY_WEEKLY_AT`, `NOTIFY_STAND_URL` | чат собственника, время недельного отчёта (`ЧЧ:ММ`, по умолчанию `09:00`), ссылка на стенд |
| `NOTIFY_DIGEST_AT` | `ЧЧ:ММ`, по умолчанию `22:00` |
| `TELEGRAM_API_URL` | необязательно: заменить `https://api.telegram.org` (тесты, прокси) |

## Известные ограничения

- В API нет чтения цен, поэтому рубли по партии оцениваются по цене за единицу из потерь продукта за последние 30 дней
  (списания, затем расхождения кассы). Нет потерь — в сообщении «нет данных о цене», в сводке такая партия считается отдельно.
- Дедупликация сообщений — в памяти процесса. При старте уже истекающие партии помечаются отправленными без сообщений (перезапуск не заваливает чат).
  но и повторно на уже отправленные событие не придёт.
- `batch.expiring` приходит один раз, поэтому упавшая отправка и разрыв SSE догоняются проходом по `/api/alerts` (каждые 30 с и после переподключения).
