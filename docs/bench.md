# Результат bench: основной алгоритм горячих предложений

Прогон: **200 seed**, 7 суток на seed, правило победителя — `спецификация`, 2.7 (`simulator.Winner`).

## Итог

- Основной алгоритм: **Bg** (`HOTOFFERS_ALGO=b`, значение по умолчанию в `internal/config/config.go`).
- Решение: ничья, ограничение прошёл только Bg. R нарушил ограничение по отказам (> +1 % заказов к C0) в клетках сценария «скоропорт-попутчик» (`scarce-companion`): M2 при u = 2.0, M1 при u = 1.5 и 2.0.
- Снижение списаний основного алгоритма — **против случайных рекомендаций (RND): 10,1 %** по сумме пяти сценариев (M2, u = 1.5), против «ближайшего срока» (C1) — 13,3 %. Против отсутствия подсказок (C0) — 10,0 %: случайные подсказки почти не отличаются от их отсутствия (в первом сценарии совпадают до рубля, в остальных — в пределах 0,3 %), поэтому две базы дают почти одну цифру. Эффект считается от RND (`спецификация`, 2.7). Данные для `GET /api/analytics/bench` — `docs/bench.json`.
- В рублях (сумма **по пяти сценариям bench**, не одного ресторана; неделя): C0 — 283 122 ₽, Bg — 254 764 ₽. R списывает ещё меньше (236 975 ₽), но нарушает ограничение по отказам, поэтому основным не становится.
- **Формулировка эффекта (одна на все документы).** Горячие предложения — второй рычаг: на партиях с излишком или коротким сроком у поставщика они снижают списания на 6–11 % (bench, 200 прогонов по 7 дней, против отсутствия подсказок), а при точной закупке — не списания, а отказы гостям: на 16 % меньше, ≈ +27 тыс. ₽ выручки (обе цифры — против той же кухни без подсказок) в месяц. Допущение: гость берёт предложенное блюдо в 30 % случаев, измеренной доли нет — проверим на пилоте. Здесь 6–11 % — сценарии «избыточная поставка» (−5,7 %) и «скоропорт в трёх блюдах» (−10,8 %) таблицы ниже; отказы и выручка — из [`pitch-numbers.md`](pitch-numbers.md).
- **Почему bench и pitchcalc дают разный эффект подсказок.** В pitchcalc закупка идёт «до уровня» под спрос, излишка почти нет — спасать нечего, подсказки дают ≈ 0,4 тыс. ₽ списаний в месяц. Профили bench построены вокруг скоропорта и излишка, там спасать есть что. Это разные ситуации, не противоречие.

## Почему основной Bg, а не R

R режет списания сильнее: в 24 клетках из 25 таблицы проверки знака R списывает не больше Bg. Но R нарушает ограничение по отказам гостям (> +1 % заказов к C0) в клетках сценария «скоропорт-попутчик» (M2 при u = 2.0, M1 при u = 1.5 и 2.0), а Bg его проходит. Правило победителя зафиксировано заранее, до прогона, — `спецификация`, 2.7 (`simulator.Winner`): сначала ограничение по отказам, потом списания. Выбирать R, потому что он «красивее» по списаниям, значило бы менять правило после результата.

## Воспроизведение

```
go run ./cmd/simulator bench -n 200
go run ./cmd/simulator bench -n 200 -json   # полный отчёт
```

Прогон детерминирован по seed (с 1 по 200). Границы: R побеждает только в `cheap-vs-dear`, в остальных четырёх сценариях разница меньше 5 % списаний C0, поэтому по сценариям — ничья, и основным идёт алгоритм, прошедший ограничение по отказам.
