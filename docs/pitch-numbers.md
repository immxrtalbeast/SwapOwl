# Цифры для питча: списания за месяц на точку

Задача FS-113, вход для FS-76. Цифры воспроизводимы: один сид и параметры — один результат.

## Как воспроизвести

```
go run ./cmd/pitchcalc -days 30 -runs 20            # сиды 1…20, доля горячих 0, 30, 60 %
go run ./cmd/pitchcalc -days 30 -runs 20 -seed0 100 # другие сиды
```

Прогон занимает около 20 секунд. Вывод ниже получен именно этой командой.

## Что и как считается

- **Симулятор.** Склад в памяти, события — генератор `internal/generator` на сиде демо (`internal/seed`): те же продукты, закупочные цены, блюда, рецепты, часы работы. HTTP и БД не участвуют. Закрытый склад `internal/simulator` всегда списывает по FEFO, а менять `internal/**` задача запрещает, поэтому `cmd/pitchcalc` держит свой склад с тремя порядками выдачи; поток событий, каталог, спрос и алгоритм горячих предложений берутся из тех же пакетов.
- **Списания** — остаток просроченных партий × закупочная цена продукта (`PriceMinorPer1000`), в рублях за 30 суток.
- **(а) «Без системы» — LIFO.** Без учёта сроков персонал берёт то, что лежит сверху, то есть последнюю привезённую партию; старая партия лежит глубже и портится. Это пессимистичная, но типичная картина для кухни без учёта. Случайный выбор партии даёт результат между LIFO и FIFO; LIFO выбран как наихудшая типичная база, поэтому разрыв с ним — верхняя оценка эффекта.
- **(б) FIFO** — по порядку прихода.
- **(в) SwapOwl** — FEFO (по сроку годности) плюс горячие предложения алгоритма `b` (`HOTOFFERS_ALGO=b`, топ-3, параметры из `simulator.DefaultConfig`).
- **Доля горячих предложений, которые гость берёт: 0, 30, 60 %.** На каждый заказ гостю предлагается одно блюдо из топ-3 горячих; с этой вероятностью гость заменяет им первую позицию заказа. Случайные числа зависят только от сида и номера заказа. 0 % — SwapOwl без влияния на гостя, только FEFO.
- **Профиль спроса** — демо-сид: около 38 заказов в сутки (в среднем 3 порции на заказ), пики на обед и ужин. Профиля «120 чеков в день» нет: цифры не масштабировались, 120 чеков в нём не заложено.
- **Поставки** — по генератору: 1–3 суток расчётного спроса, скоропортящиеся ежедневно. Абсолютные списания (сотни тысяч ₽) отражают именно эту избыточную закупку демо-сида; для питча надёжнее разница между режимами.

## Как читать

- FEFO и FIFO дают **одинаковый** результат (строка «берут 0 %» равна FIFO): у одного продукта все поставки имеют один срок хранения, значит порядок прихода и порядок сроков совпадают. Выигрыш SwapOwl над FIFO в этих данных целиком даёт горячая рекомендация, а не FEFO. FEFO важен, когда у партий одного продукта разные сроки (остаток старой партии, партия с коротким сроком).
- Разброс по сидам (σ) около 46–48 тыс. ₽, но разница считается парно на одном сиде, поэтому её интервал уже. Все различия с «берут 30 %» и «берут 60 %» вне интервала; «берут 0 %» − FIFO — ровно 0 (разница внутри разброса, эффекта нет).
- Эффект горячих предложений зависит от доли гостей, которые их берут. При 0 % его нет. Эта доля — допущение, измеренной у нас нет; её надо проверять на пилоте.
- Модель не учитывает цену блюда и выручку, только списания по закупочной цене.

## Фраза для слайда

> ≈ 150 тыс. ₽ в месяц на точку (−20 % списаний к «без системы»; −15 % к FIFO) при допущениях: демо-профиль ≈ 38 заказов в сутки, закупочные цены демо-каталога, гость берёт 30 % горячих предложений, 20 прогонов (сиды 1…20), среднее. Без горячих предложений (0 %) выигрыш над FIFO нулевой, над «без системы» (LIFO) ≈ 45 тыс. ₽.
