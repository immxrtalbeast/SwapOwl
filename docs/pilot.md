# Прогон перед пилотом: 30 дней ресторана через адаптер

Тест `tests/pilot` (`TestPilotThirtyDays`) — доказательство готовности к подключению ресторана
(`.ai/solution.md`, 8.0а; план 3б.11). Он гонит 30 симулированных суток по цепочке, которая будет в
пилоте:

```
фейковый iiko ──► cmd/iiko-adapter ──► cmd/api (PostgreSQL)
       ▲                                    │
       └──────── стоп-лист через outbox ────┘
```

Всё запускается как отдельные процессы на чистой базе: `cmd/api` с `CLOCK_MODE=simulated` и
`AUTH_REQUIRED=true`, адаптер в боевом режиме (`ADAPTER_MODE=live`) с ключом API роли `operator`,
фейковый iiko из `internal/iiko/fake`. Часы стенда стоят на паузе, время двигает только тест.

## Запуск

```bash
export TEST_DATABASE_URL='postgres://user:pass@localhost:5432/postgres?sslmode=disable'
go test -race -p 1 -timeout 20m ./tests/pilot/...
```

Тест сам создаёт и удаляет отдельную базу. Без `TEST_DATABASE_URL` он пропускается. Прогон занимает
около минуты.

Прогон не зависит от часов машины: история iiko начинается с начала суток 2026-10-12 (Europe/Moscow), часы
стенда стартуют на паузе в 11:00 этого дня (момент записывается в `clock_state` до рабочего запуска), поэтому
полночь по часам машины ничего не пропускает.

## Что происходит за сутки (время ресторана, Europe/Moscow)

| Время | Событие |
|---|---|
| 00:30 | Проход адаптера. Сверка с iiko за вчера |
| 08:00 | В iiko приходит накладная |
| 09:30 | Проход адаптера: накладная принята с опозданием 1,5 ч (в пределах окна `LATE_EVENTS_HOURS=4`; в день 0 стенд стартует в 11:00, накладной 08:00 нужно окно больше 3 ч), `occurred_at` = 08:00 |
| 11:00–21:30 | Проход адаптера каждые 1,5 ч: продажи уходят заказами `pos` по чекам с `occurred_at` = время чека (окно не пропускает более старые) |
| 14:00 | Четыре заказа через API, отмена принятого заказа, брак с партии (`spoilage`/`damage`); раз в 5 дней — поздняя накладная вручную (90 мин — принимается, 5 ч — отказ без записи); на 6-е, 16-е и 26-е сутки — отмена заказов кассы за вчера |
| 22:30 | Инвентаризация одного продукта (по кругу) с небольшим расхождением: чаще недостача 1–3 %, раз в четыре дня — излишек |
| 22:30–23:30 | Проход адаптера: стоп-лист уходит в iiko. Проверки конца дня |

Срок годности идёт по настоящему расписанию стенда: за 30 суток просрочились и были списаны
«дворником» 173 партии.

## Проверки

В конце каждых суток (23:30):

1. **Ни одного `5xx`** — ни на запросах теста, ни на запросах адаптера (по журналу сервиса), ни `panic`.
2. **Журнал движений сходится с остатками** по каждой партии:
   `receipt + return − sale − writeoff − adjustment = remaining`, `0 ≤ remaining ≤ quantity`.
3. **Стоп-лист в iiko совпадает с `GET /api/stop-list`.**
4. **В outbox нет недоставленного.**

После полуночи, на сверке за закрытые сутки:

5. **Источники дошли целиком**: порции по блюдам в заказе кассы за день равны продажам в iiko, каждая
   накладная iiko есть у нас поставкой с тем же `id`.
6. **Сверка с iiko (`iiko-adapter reconcile`)**: проверяется *сдвиг за сутки* расхождения «наш остаток −
   остаток iiko» по каждому продукту — от остатка начала суток (прошлой сверки), а не от начала прогона.
   Сдвиг объясняется только тем, что сценарий задал за эти же сутки: заказы через API и их отмены, брак,
   инвентаризация, поздние накладные; а также срок годности (iiko его не знает) и недостачи продаж
   кассы. Без недостач и положительных отклонений за сутки сдвиг обязан совпасть с заданным точно
   (допуск 2 базовые единицы — округление остатка iiko); иначе допуск — сумма недостач и положительных
   отклонений (отмены, излишки) **только за эти сутки**: продажа кассы «съедает» часть расхождения, когда
   продукта не хватает с одной стороны. Допуск не копится за 30 дней, поэтому ошибка в 1 % в день
   не прячется.
7. **Срок партии считается от даты накладной iiko**: `received_at` каждой партии равен `dateIncoming`
   накладной (08:00), хотя принята она в 09:30, а `expires_at` — `received_at` + срок хранения продукта
   из iiko.

## Чего прогон не доказывает

- Это фейковый iiko: форматы и ограничения реального iikoServer проверяются при подключении
  (`docs/iiko.md`, список `[ПРЕДПОЛОЖЕНО]`).
- Фейк генерирует поставки, не привязанные к спросу, поэтому много продукта пропадает по сроку
  (573 620 из ~1 350 000 г/мл/шт); для сверки это полезно (расхождение по сроку есть каждый день), как
  оценка реальных потерь — нет.
- Часы адаптера в тестовой сборке подменены (`go build -overlay`, исходники не меняются): боевой
  адаптер читает `time.Now()`, а прогон идёт на ускоренных часах стенда. Логика синхронизации, сверки
  и outbox — та же, что в `cmd/iiko-adapter`.
- Перед адаптером стоит прокси, который не отдаёт накладные «из будущего»: фейк отдаёт накладные
  за дату целиком, настоящий iiko знает только о проведённых документах.
- Адаптер передаёт `occurred_at` (FS-111): накладная — по дате iiko, продажа — по времени чека. Прокси
  не отдаёт и чеки, закрытые позже «сейчас». Поздние накладные вручную по-прежнему идут прямыми
  запросами к API.
