# Заготовки и полуфабрикаты (roadmap)

> **Статус: не реализовано.** В этой версии нет ни кода, ни миграций, ни API, ни экрана для заготовок. Документ описывает, как ступень «заготовка» встала бы в систему. В «Лестнице спасения» (`GET /api/rescue-ladder`) эта ступень отдаётся без расчёта: `kind: "prep"`, `status: "roadmap"`, `detail: "Пока не в этой версии"`, поэтому `best` её никогда не выбирает.

## Что это

Заготовка — продукт, переработанный на кухне заранее и живущий по собственному сроку и с собственным выходом:

| Исходный продукт | Заготовка | Что меняется |
|---|---|---|
| мясо, рыба | маринад | свой срок, выход близок к 100 % |
| овощи | нарезка | свой срок (короче), выход < 100 % из-за очистки |
| соус | порции | свой срок, выход ≈ 100 % |

Смысл для спасения партии: партия, которую не успеть продать целиком, превращается в заготовку с другим сроком, и «обречённое» количество получает ещё один шанс. Сегодня сервис знает только закрытую и вскрытую упаковку.

## Чем похоже на вскрытие упаковки

Вскрытие (`docs/opened.md`) уже даёт готовую модель:

- исходная партия делится, часть уходит в **дочернюю партию** (`parent_batch_id`);
- у дочерней есть момент операции (`opened_at`) и пересчитанный срок `expires_at = min(исходный срок, now + shelf_after_open_hours)`;
- перенос пишется парой движений, суммарный остаток продукта не теряется;
- FEFO не меняется, дочерняя партия с ранним сроком уходит первой;
- операция идемпотентна по ключу `(kind, id)` в `corrections`.

Отличия заготовки:

1. **Другой продукт.** Дочерняя партия относится к продукту-заготовке (`marinated_salmon`), а не к исходному.
2. **Выход.** Количество на выходе — `q × yield`, а не `q`.
3. **Срок только от операции.** `expires_at = min(исходный срок, now + shelf_hours_заготовки)`: заготовка не может жить дольше сырья. Это правило то же, что у вскрытия, только срок берётся из рецепта заготовки.
4. **Единицы.** Заготовка может иметь другую единицу (кг → порции).

## Журнал движений

Новый вид движения `process` (`movements.kind` без CHECK, см. `0001_init.sql`, так что миграция не нужна):

- родитель: `process`, `−q`, причина `prep`;
- дочерняя партия: `process`, `+q × yield`, причина `prep`.

Баланс партии с учётом нового вида:

```
receipt + transfer_in + return + process_in − sale − writeoff − adjustment − transfer_out − process_out = remaining
```

**Сторож №1 должен остаться.** Он проверяет сохранение количества по каждой партии. Для заготовки это выполняется, если «приход» дочерней партии — единственное движение `process_in` ровно на `quantity`, а у родителя `process_out` уменьшает `remaining`, не трогая `quantity` (как `transfer_out` при вскрытии). Сохранение по продукту (`Σ in = Σ out`) для `process` не выполняется из-за выхода: суммарный остаток продуктов меняется на `q × (yield − 1)`. Поэтому новый вид нельзя «спрятать» под `transfer_*`: нужна отдельная формула в сторожe, а сторожа меняют только люди (строка `INVARIANT-CHANGE`). Эту правку в этой задаче не делаем.

## Затронутые инварианты

| № | Что с ним |
|---|---|
| 1 Сохранение количества | Меняется формула (выше). Требует решения человека. |
| 4 Дворник | Просрочка дочерней партии идёт тем же путём, нужен тест гонки операции и границы срока. |
| 5 FEFO | Не меняется. |
| 6 Граница срока | Не меняется; срок дочерней партии считается так же. |
| 8 Стоп-лист | Заготовка как ингредиент блюда: остаток продукта-заготовки входит в пересчёт; нужен рецепт, где блюдо использует заготовку. |
| 9 Идемпотентность | Операция обязана быть идемпотентной (ключ `(process, id)`). |
| 10–11 Горячие предложения | Заготовки как продукты участвуют, как обычные; монотонность по сроку сохраняется. |

## API-набросок

`POST /api/batches/{id}/process` (роль `operator`):

```json
{ "id": "proc-001", "qty": "600", "unit": "g", "prep_product_id": "marinated_salmon" }
```

Ответ `201`: `{ "parent_batch_id": 17, "child_batch": { ... }, "yield_qty": "570", "expires_at": "..." }`. Повтор с тем же телом — `200`, `replayed: true`. Другое тело с тем же `id` — `409 correction_conflict`.

Ошибки по образцу вскрытия: `409 batch_closed`, `400 validation_error` (qty больше остатка, чужая единица, нет рецепта заготовки), `404 unknown_batch`.

Данные: справочник рецептов заготовок `preps(product_id, prep_product_id, yield_num, yield_den, shelf_hours)`; допуск `parent_batch_id` у партий уже есть, `opened_at` для заготовки можно переиспользовать как «момент операции» или завести `processed_at`.

## Экран

- в карточке партии (журнал партий) кнопка «В заготовку» с выбором заготовки, количеством и показом ожидаемого выхода и срока;
- в «Лестнице спасения» (`#/ladder`) ступень «Заготовка» перестаёт быть заглушкой: `saved_minor` — стоимость сырья, которое успеют использовать, `cost_minor` — труд и потери выхода.

## Что не реализовано (честно)

- Нет операции `process`, вида движения, рецептов, миграции, API и кнопки на экране.
- В лестнице ступень `prep` — всегда `status: "roadmap"` без `saved/cost/net`; в расчёт `best` не входит.
- Сторож №1 не знает про `process`; пока нет операции — менять его не нужно.
- Выход, сроки заготовок и стоимость труда — допущения для оценки, на реальных данных кухни не проверялись.
