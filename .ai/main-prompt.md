# Правила проекта: мониторинг остатков, сроков годности и стоп-листов

Этот файл читают все агенты. Он задаёт архитектуру, словарь домена, инварианты и принятые решения. Если что-то здесь противоречит `.ai/solution.md`, прав `solution.md` — он новее; сообщи о расхождении в комментарии к таске.

Связанные файлы: `.ai/plan.md` — план работ и таски; `.ai/solution.md` — решение целиком, в том числе доступ, HTTPS, журналы и CI/CD (раздел 2.9) и правила, чтобы не закрыть дорогу к подключению ресторанов (раздел 8.2).

## Что строим

Сервис учёта склада ресторана: принимает поставки партиями, хранит остатки и сроки годности по каждой партии, проверяет и списывает ингредиенты при заказе, автоматически ведёт стоп-лист блюд, предупреждает об истекающих партиях, предлагает поставки и формирует список «горячих предложений» — блюд, продажу которых стоит стимулировать, чтобы не списывать продукты.

Критерии жюри, в порядке, в котором по ним чаще всего теряют баллы:
1. Корректная работа со сроками годности и партиями.
2. Работа стоп-листа при недостатке ингредиентов.
3. Качество алгоритма горячих предложений.
4. Стабильность и качество реализации.
5. Приятная вёрстка и дизайн.

## Архитектура

- `internal/domain` — чистая логика: партии, FEFO, проверка и списание, стоп-лист, мониторинг сроков, предложение поставок. Не знает о БД, сети и текущем времени.
- `internal/hotoffers/a`, `internal/hotoffers/b` — две версии алгоритма горячих предложений за одним интерфейсом. Чистые функции.
- `internal/store` — Postgres, миграции, транзакции.
- `internal/clock` — интерфейс часов: реальные, фиксированные (тесты), ускоренные (симулятор и демо).
- `internal/config` — конфигурация из переменных окружения (`solution.md`, 7.6) и проверки при старте. Параметры ресторана читаются только отсюда.
- Пакет сида (`internal/seed`) и пакет генератора событий (`internal/generator`) — справочники, история и поставки/заказы для стенда и симулятора. Общие для `cmd/simulator` и демо-панели; ядро (`internal/domain`, `internal/store`, хендлеры вне `/api/demo/*`) их не вызывает и о них не знает (`solution.md`, 8.2).
- `cmd/api` — HTTP JSON API и SSE-поток событий. Бизнес-логики в хендлерах нет.
- `cmd/simulator` — генератор поставок и заказов с seed и множителем скорости времени.
- `frontend/` — React. Бизнес-логику не считает: стоп-лист, сроки и рекомендации приходят с бэкенда.
- `tests/invariants/` — тесты-сторожа. Меняют только люди.
- `e2e/` — Playwright, демо-сценарий.

## Словарь домена

- **Продукт** — тип ингредиента: id, название, единица измерения (`g`, `ml`, `pcs`).
- **Поставка** — id (уникальный, от поставщика), номер, дата создания, список позиций.
- **Партия** — то, что пришло одной позицией поставки: продукт, количество, дата поступления, срок годности `expires_at`, текущий остаток. Остаток склада по продукту — это сумма остатков его непросроченных партий, и никак иначе.
- **Блюдо** и **рецепт** — список продуктов и количество каждого на одну порцию.
- **Заказ** — одно или несколько блюд с количеством порций.
- **Стоп-лист** — блюда, для которых нельзя собрать ни одной порции из непросроченных остатков.
- **Истекающая партия** — партия, у которой осталось меньше порога срока (см. решения).
- **Количество под риском** — часть остатка партии, которую не успеют израсходовать до истечения при обычном спросе.
- **Горячее предложение** — блюдо с приоритетом и объяснением, ссылающимся на конкретные партии.

## Инварианты

Каждый закреплён тестом в `tests/invariants/`. Если тест падает — ошибка в коде, а не в тесте.

1. **Сохранение количества.** Поступило − списано = сумма остатков по партиям. Ни одна партия не уходит в минус.
2. **Атомарность заказа.** Потребность суммируется по всем блюдам заказа. Заказ через наш API (`source: "api"`, по умолчанию) либо списывает всё, либо ничего. Продажа из кассы (`source: "pos"`) уже состоялась: она списывает по FEFO всё доступное, недостачу записывает расхождением без партии и принимается всегда; ни одна партия не уходит в минус (`solution.md`, 2.3а).
3. **Конкурентность.** Параллельные заказы не продают одну порцию дважды.
4. **FEFO и просрочка.** Списание идёт с партии с ближайшим сроком. Просроченная партия не участвует ни в списании, ни в доступности.
5. **Стоп-лист — функция остатков.** После любого события, включая наступление срока без других событий, стоп-лист равен пересчёту с нуля.
6. **Горячие предложения допустимы.** В списке нет блюд из стоп-листа; у каждой рекомендации есть объяснение со ссылкой на партию.

Плюс одно правило с обычным тестом, не сторожем: приём поставки идемпотентен — повторная отправка поставки с тем же id не увеличивает остатки.

## Решения по неоднозначностям

Согласованы с таблицей раздела 5 `.ai/solution.md`; подробности и граничные случаи — там.


- **Срок хранения.** В поставке приходит длительность хранения; `expires_at = received_at + длительность`, где `received_at` — время стенда в момент приёма. Если пришла абсолютная дата — используется она. `created_at` поставки в расчёте срока не участвует. Решение описано в README.
- **Единицы.** Количества хранятся целыми числами `int64` в базовых единицах (граммы, миллилитры, штуки). Никаких float в остатках и рецептах. Конвертация единиц — в одном месте.
- **Заказ.** Отказ — для всего заказа целиком, с перечнем недостающих продуктов в ответе. Исключение — продажа из кассы (`source: "pos"`): отказа нет, недостача — расхождение (`solution.md`, 2.3а).
- **Списание.** FEFO — строгое правило, не рекомендация. Ответ на заказ показывает, из каких партий что списано.
- **Порог «истекает».** Осталось меньше `min(max(20% полного срока, 12 часов), 50% полного срока)`, срок = `expires_at − received_at`. Все три значения в конфиге.
- **Часовой пояс.** Один часовой пояс ресторана, в конфиге. Дата «годен до 12 октября» означает конец этого дня по местному времени.
- **Просроченные партии.** Доступность определяет предикат времени (`now < expires_at`), а не событие. Событие списания с причиной «истёк срок» пишется со временем `expires_at`; партия не участвует в доступности, даже если событие ещё не записано.
- **Время.** Нигде в `internal/domain` и `internal/hotoffers` нет вызова `time.Now()`: время приходит аргументом через `clock.Clock`.

## Общие правила

- Каждая таска делает одно дело. Если по ходу нашлось другое — комментарий в Jira, а не расширение объёма.
- Любое изменение поведения сопровождается тестом.
- Секретов в коде, логах и URL нет; конфиг — через переменные окружения.
- Если меняется API или формат данных — это отдельная таска на контракт, а не попутная правка.
- README обновляется в том же PR, если меняется запуск, конфиг или API.
