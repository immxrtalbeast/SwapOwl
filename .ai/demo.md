# Демо-сценарий на 5 минут

Из этого сценария пишется `e2e/` (Playwright). Каждый шаг: действие → что должно быть на экране → проверка для e2e. Названия продуктов, блюд и числа — из сида; сид обязан обеспечить указанные ниже условия.

## Условия сида (состояние сразу после сброса, время стенда `T0` = 11:00)
- Лосось: партия Л-1, 2 кг, принята 3 суток назад, истекает через 5 ч (в `T0` уже в статусе «истекает»); партия Л-2, 4 кг, истекает через 3 суток.
- Сливки: партия С-1, 600 мл, истекает через 26 ч; других партий нет.
- Блюда: «Паста с лососем» (лосось 150 г, сливки 100 мл, паста 120 г), «Стейк из лосося» (лосось 200 г), «Крем-суп» (сливки 200 мл, картофель 250 г), ещё не менее пяти блюд без лосося и сливок.
- Остальных продуктов хватает не менее чем на 40 порций каждого блюда.
- История: 14 дней заказов; априорный спрос задан так, что партия Л-1 при обычном спросе не расходится до срока.
- Симулятор остановлен, скорость ×1. Токен демо введён в демо-панели.
- Демо-профиль симулятора (фиксированный seed) за шаг 1 не заказывает блюда со сливками, поэтому перед шагом 5 сливок остаётся ровно на `S` порций «Крем-супа», `1 ≤ S ≤ 5`. e2e читает `S` из `GET /api/dishes` перед шагом 5 и не полагается на константу.

## Шаги

| № | Время | Действие | На экране | Проверка e2e |
|---|---|---|---|---|
| 0 | до показа | Сброс стенда кнопкой демо-панели | Время стенда 11:00, стоп-лист пуст | `POST /api/demo/reset` → `200`; `GET /api/stop-list` → пустой список |
| 1 | 0:00–0:30 | Запуск симулятора на ×600; через ~10 с пауза | Остатки на экране «Склад» убывают без перезагрузки, время стенда бежит; изменившиеся строки подсвечиваются | Остаток хотя бы одного продукта изменился без перезагрузки страницы; индикатор связи «на связи» |
| 2 | 0:30–1:00 | Открыть ленту предупреждений в шапке | Партия Л-1 в статусе «истекает», счётчик предупреждений ≥ 1; строка партии окрашена цветом срочности | В ленте есть запись с номером партии Л-1; статус партии в `GET /api/batches` — `expiring` |
| 3 | 1:00–1:40 | Клик по предупреждению → экран «Горячие предложения» | Первая карточка — блюдо с лососем; на карточке: партия Л-1, количество под риском, время до срока, цель в порциях. Блюд из стоп-листа нет | Первая рекомендация содержит `batch` = Л-1 и цель > 0; ни одного блюда из `GET /api/stop-list` |
| 4 | 1:40–2:20 | Экран «Заказы»: заказ «Паста с лососем» ×2 + «Стейк из лосося» ×1 | Заказ принят; в ответе: лосось 500 г списан из партии Л-1 (не из Л-2), сливки 200 мл из С-1 | `201`; в `writeoffs` все строки по лососю — партия Л-1; остаток Л-2 не изменился |
| 5 | 2:20–3:00 | Демо-панель: «10 параллельных заказов» на «Крем-суп» (сливок осталось на `S` порций, по сиду `S` = 2) | Ровно `S` заказов приняты, остальные отклонены с причиной «не хватает сливок» и числами; остаток сливок 0; «Крем-суп» и «Паста с лососем» — в стоп-листе с причиной | 10 одновременных POST: `S` × `201`, `10 − S` × `409 insufficient_stock`; остаток сливок = 0 и нигде не отрицателен; оба блюда в `GET /api/stop-list` |
| 6 | 3:00–3:40 | Демо-панель: прыжок времени +6 ч | Без перезагрузки: в журнале списаний — остаток партии Л-1 с причиной «истёк срок»; остаток лосося уменьшился; горячие предложения перестроились | Движение `writeoff`/`expired` по Л-1 с временем = `expires_at`; `remaining` Л-1 = 0; время стенда = прежнее + 6 ч |
| 7 | 3:40–4:10 | Экран «Поставки» → «Предложение поставок» | Сливки — первой строкой: блокируют 2 блюда, предлагаемое количество, объяснение с числами | Первый элемент `GET /api/supply-suggestions` — сливки, `quantity` > 0, `blocks_dishes` = 2 |
| 8 | 4:10–4:40 | Принять поставку сливок кнопкой «Принять предложенное»; затем «Отправить ещё раз» | После первой отправки: новая партия сливок, «Крем-суп» и «Паста с лососем» вышли из стоп-листа. После второй: сообщение «Поставка уже принята», остаток тот же | Первый POST → `201`; второй с тем же телом → `200`, `replayed: true`; остаток сливок одинаков после обоих; стоп-лист пуст |
| 9 | 4:40–5:00 | Экран «Аналитика» | Одна цифра: на сколько основной алгоритм снижает списания против случайных рекомендаций, с числом прогонов; ниже — график списаний по причинам | Блок сравнения присутствует и содержит число и количество прогонов. Если bench не готов к дню 4 — шаг заменяется графиком списаний, утверждения о сравнении нет |

## Запасные ходы
- Шаг 5 не уложился или сеть на площадке плохая: показывается заранее записанный результат того же действия на экране «Заказы» (история отклонённых заказов) и тест-сторож №3 в CI.
- Шаг 1 не нужен жюри (нет времени): начинать с шага 2, симулятор запустить после шага 9 на вопросах.
- Вопрос «а если я отправлю сам?»: в README — три команды `curl` (поставка, заказ, повтор поставки), работающие при любом времени стенда.

## Что подготовить для Go-разработчика из жюри (в репозитории, не в демо)
- `PlanWriteoff` — чистая функция с табличными тестами.
- `tests/invariants/` и строка запуска `go test -race ./...` в CI.
- Раздел README «Решения по неоднозначностям» и абзац «почему блокируется продукт, а не партия» со ссылкой на сторожа №3 и №4.
