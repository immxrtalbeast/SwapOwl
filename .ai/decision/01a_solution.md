# 01a — независимое решение автора (Opus)

## Идея в одной фразе
Склад — это журнал движений по партиям плюс одно правило доступности `остаток > 0 и now < expires_at`; всё остальное (остатки, стоп-лист, «истекает», предложение поставок, горячие предложения) — чистые функции от снимка «партии + рецепты + спрос + время», которые считаются при чтении и поэтому не могут разойтись со складом.

## Как устроено
- **Go + Postgres + React**, один процесс API (`net/http` Go 1.22, `pgx`), SSE из процесса. Один экземпляр — осознанно: ресторану хватает, а in-process рассылка событий не требует брокера. [ПРЕДПОЛОЖЕНО: жюри не ждёт горизонтального масштабирования]
- **Поставка** → по партии на позицию. `expires_at` считается один раз при приёме и хранится. Идемпотентность: PK по внешнему id + хэш тела; повтор с тем же телом → `200` и `replayed:true`, с другим телом → `409`. Партии создаются в той же транзакции, что и запись поставки.
- **Заказ**: потребность суммируется по всем блюдам → транзакция → блокировка строк *продуктов* в порядке id (`FOR UPDATE`), затем чтение их непросроченных партий → чистая функция домена строит план FEFO `(expires_at, batch_id)` → либо применяется весь план, либо `409` со списком нехватки. Блокировка по продукту, а не по партиям: порядок блокировок очевиден, дедлок невозможен, новая партия не «проскакивает» мимо блокировки. `CHECK (remaining >= 0)` — страховка в БД. Заказ идемпотентен по клиентскому id.
- **Время**: один `clock.Clock`; симулированное время монотонно и переживает рестарт (смещение хранится в БД), иначе после перезапуска просроченные партии «оживут». Граница строгая: партия доступна, пока `now < expires_at`.
- **Просрочка**: корректность не зависит от фонового процесса — просроченная партия исключается предикатом в каждом запросе. Фоновый «дворник» лишь материализует списание (движение `writeoff/expired` с временем = `expires_at`, остаток → 0) и шлёт SSE; спит до ближайшего `expires_at`.
- **Стоп-лист** = блюда, у которых `min по ингредиентам floor(доступно / норма) = 0`; считается при чтении, с причиной (каких продуктов не хватает и сколько).
- **Единицы**: в БД и домене — `int64` в `g|ml|pcs`. На входе API — десятичная строка + единица (`"1.5" kg`), разбор без float в одном пакете; несовпадение размерности, дробь мельче базовой единицы, ноль/минус, переполнение → `400`.
- **Предложение поставок** (обязательный пункт мониторинга): по каждому продукту — средний дневной расход за окно (включая спрос отклонённых заказов), проекция FEFO-расхода вперёд с учётом того, что часть запаса истечёт раньше, чем будет съедена; `к заказу = спрос за (срок доставки + дни покрытия) − пригодный запас`, округление до упаковки, дата ожидаемого обнуления и объяснение. Продукты, из-за которых блюдо уже в стоп-листе, — наверху.

## Горячие предложения (пятая часть оценки)
Общая основа — **количество под риском** партии: остаток минус то, что обычный спрос успеет съесть до `expires_at` (проекция FEFO). Без неё «горит» всё подряд, включая то, что и так продастся.
- **A, скоринг**: приоритет блюда = Σ по рисковым партиям его ингредиентов `срочность(t) × доля риска, которую блюдо реально может поглотить`, поделённая на число блюд-конкурентов за этот продукт. Прозрачно, объяснимо, монотонно по сроку — буква кейса.
- **B, жадное распределение**: на каждом шаге выбирается блюдо с максимальной спасённой стоимостью на порцию, виртуальные остатки уменьшаются по *всем* ингредиентам, прирост пересчитывается. На выходе не только порядок, но и цель: «продать ещё 12 порций до 18:00, спасёт 3,4 кг лосося из партии №…».
- **Сравнение**: офлайн-режим симулятора гоняет чистый домен в памяти (без БД, тысячи симулированных дней за секунды) на одинаковых seed. Модель: базовый спрос по блюдам + подъём спроса для top-k горячих. Контроли: «без рекомендаций» и «наивно по ближайшему сроку». Метрики: доля списанного от поступившего, стоимость списаний, отказы. Парное сравнение по seed, сетка значений подъёма спроса — потому что величина подъёма выдумана. [НАДЕЮСЬ: вывод «B лучше A» устойчив к модели спроса]

## Демо за 5 минут
Две партии одного продукта → заказ списывает по FEFO и показывает партии → 10 параллельных заказов на последние 3 порции: ровно 3 успеха → прыжок времени: партия истекла, блюдо в стоп-листе, списание в журнале, всё без перезагрузки → горячие карточки с целью в порциях → предложение поставок → страница «A против B» с цифрами списаний.

## Чего не делаем
Авторизацию по ролям, CRUD справочников (сид + автосоздание продукта из поставки), отмену заказов, Grafana, несколько экземпляров API.
