## 1. Конкурентность и время

| Претензия | Решение | Довод и что меняется |

| B зона 1: «дворник» без блокировки продукта теряет обновление, с обратным порядком — дедлок; A-П8 то же | **Принята** | Эксперименты 1.2 и 1.3 Скептика воспроизводят оба исхода; текст 2.4 действительно говорит только «в транзакции». Новое правило: **любая транзакция, меняющая `batches` (заказ, поставка, дворник, прыжок времени, сброс), первой командой блокирует затронутые продукты `FOR UPDATE` в порядке id**. Запись остатка — относительная: `SET remaining = remaining - $x WHERE id = $id AND remaining >= $x`, число затронутых строк проверяется. Сторож: «дворник + 50 заказов на границе истечения». |
| B: `now` взят до ожидания блокировки | **Принята** | Логически верно: при скорости ×3600 две секунды ожидания = два часа. `now` берётся из часов **после** получения блокировок продуктов и записывается в заказ как его время. |
| B: порядок `ORDER BY … FOR UPDATE` подтверждён, но не документирован | **Принята как P2** | Блокируем циклом по отсортированному списку id (один запрос на продукт) — порядок не зависит от плана. Заказ затрагивает единицы продуктов, цена нулевая. |
| B: идемпотентность заказа — проверка до транзакции, нет `409` для другого тела | **Принята** | Первая команда транзакции — `INSERT INTO orders … ON CONFLICT (id) DO NOTHING`; 0 строк → читаем сохранённый заказ, сравниваем хэш тела: совпал — отдаём сохранённый ответ, не совпал — `409 order_conflict`. Отказ по нехватке **не откатывает** транзакцию: план считается до любой записи в партии, поэтому заказ фиксируется со статусом `rejected` и перечнем нехватки, а партии не тронуты. |
| A-П10 (P2): повтор отклонённого заказа остаётся отказом | **Принята** | Это и есть идемпотентность. В контракт: «новая попытка — новый id»; форма заказа генерирует id на каждое нажатие. |
| B: база срока `created_at` (будущее / прошлое / без зоны); A-П7: жюри шлёт поставку с реальной датой на стенд с ушедшими часами | **Принята, решение меняется** | Возвращаюсь к значению по умолчанию из `main-prompt.md`: `received_at = clock.Now()` в момент приёма, `expires_at = received_at + длительность`. `created_at` хранится как реквизит документа и в расчёте не участвует — запрос через curl с сегодняшней датой работает при любом времени стенда. Каждый ответ API несёт текущее время стенда. Моё допущение «дата создания ≈ дата поступления» снимается. |
| B: монотонность часов без механизма | **Принята** | Состояние часов в БД: `(sim_base, wall_base, speed)`; `now = sim_base + (wall − wall_base) × speed`. Смена скорости и прыжок перебазируют обе точки; отрицательный прыжок — `400`; пауза = скорость 0. Тест рестарта. |
| B (P2): начало дня в зоне с переводом часов в полночь | **Принята как P2** | Утверждение «корректно при любой смене смещения» снимаю. Зона задаётся конфигом и проверяется при старте; тесты — Europe/Moscow и Europe/Berlin. |
| C-П10б (P2): убрать `expires_on`, оставить только длительность | **Отвергнута** | Абсолютная дата и правило конца дня — уже принятое правило проекта (`main-prompt.md:57,62`), tzdata вшивается одной строкой (подтверждено экспериментом 2 Скептика). Выигрыш от удаления меньше риска вопроса жюри «а если на упаковке дата?». |
