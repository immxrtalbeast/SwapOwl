# 01 — Решение (после вердикта KEEP WITH CHANGES)

Слияние `01a_solution.md` (автор) и `01b_solution_external.md` (внешняя модель), исправленное по `03_verdict.md`. Метки допущений: [ПРОВЕРЕНО] — следует из кейса, правил проекта или эксперимента в дебате; [ПРЕДПОЛОЖЕНО] — разумно, не проверено; [НАДЕЮСЬ] — может не сбыться.

## 1. Что делаем
Web-сервис учёта склада ресторана: Go (API + SSE) + PostgreSQL + React, один экземпляр API. Срок — 7 дней, 4 человека, 5 агентов-исполнителей. [ПРОВЕРЕНО: стек рекомендован кейсом, `00_case.md:124-129`] [ПРЕДПОЛОЖЕНО: одного экземпляра достаточно]

Опорная идея: **склад — это партии и журнал движений; доступно то, у чего `remaining > 0` и `now < expires_at`**. Остатки, стоп-лист, статус «истекает», предложение поставок и горячие предложения — чистые функции от снимка (партии, рецепты, история спроса, время). Они считаются при чтении и не хранятся как состояние, поэтому не могут разойтись со складом.

## 2. Как

### 2.1 Поставки и партии
- Поставка: внешний `id` (уникальный), `number`, `created_at`, позиции `{product_id, name, quantity, unit?, срок хранения}`. Одна позиция = одна партия; две позиции одного продукта в одной поставке — две партии.
- Срок хранения в позиции — ровно одно из двух: `shelf_life_hours` (целое, 1…87600) или `expires_on` (`YYYY-MM-DD`). Оба сразу или ни одного — `400`.
- `received_at = clock.Now()`, взятое **после** получения блокировок продуктов. `expires_at` считается один раз при приёме и хранится: `received_at + shelf_life_hours` либо начало следующего дня после `expires_on` по времени ресторана (сам момент — уже просрочено). `created_at` — реквизит документа, в расчёте срока не участвует; это записано в README и видно в карточке партии. [ПРОВЕРЕНО: значение по умолчанию `main-prompt.md:57`]
- На каждую партию пишется движение `receipt`. Позиция, уже просроченная в момент приёма (возможно только с `expires_on`), принимается и сразу списывается движением `writeoff`/`expired` с временем `= received_at` (не `expires_at`: списание не может стоять в журнале раньше прихода); в ответе — предупреждение и текущее время стенда.
- Продукты и их базовые единицы приходят из сида. `unit` в позиции необязателен: если его нет, берётся базовая единица продукта. Неизвестный продукт создаётся из поставки только при явном `unit` (`INSERT … ON CONFLICT DO NOTHING`, затем сверка единицы); без `unit` — `400` с примером. Автосозданный продукт получает справочную цену 0 и не входит ни в один рецепт.
- **Повторная отправка.** PK по `id` + хэш тела; запись поставки и партий — одна транзакция, `INSERT … ON CONFLICT DO NOTHING`. Хэш считается от доменной структуры после нормализации в базовые единицы: `id, number, created_at` и позиции `(product_id, количество в базовых единицах, срок в том виде, в каком пришёл: часы или дата)`, отсортированные по этой тройке; `name` в хэш не входит. Тот же id и тот же хэш → `200`, `replayed: true`, сохранённый ответ, остатки не меняются. Тот же id и другой хэш → `409 delivery_conflict`. Одновременные одинаковые запросы: один создаёт, второй получает replay. [ПРОВЕРЕНО: `r1_B` эксп. 1.4]

- **Порядок шагов транзакции приёма:** (1) `INSERT` поставки `ON CONFLICT DO NOTHING`; 0 строк → сравнение хэша и replay либо `409`; (2) автосоздание неизвестных продуктов; (3) блокировка продуктов поставки по протоколу 2.3 (уникальный отсортированный список id); (4) `received_at = clock.Now()`; (5) партии и движения `receipt`; (6) сохранение ответа.

### 2.2 Единицы
- В БД, домене и ответах API — `int64` в базовых единицах `g | ml | pcs`. Никаких float.
- На входе `quantity` — **только JSON-строка** вида `^[0-9]+(\.[0-9]+)?$`, `unit` ∈ `g, kg, ml, l, pcs`. Собственный разбор в `internal/domain/units`; `ParseFloat` и `big.Rat` не используются. `400`: JSON-число, знак, экспонента, запятая, пустая дробная часть; размерность не совпадает с продуктом; дробь мельче базовой единицы; дробные `pcs`; ноль; превышение предела.
- Вся арифметика количеств — через проверенные `Add`/`Mul` из `units` (ошибка при переполнении). Пределы: количество ≤ `10^12` базовых единиц, порций в позиции заказа ≤ `10^4`.
- Рецепт хранит норму в базовой единице продукта. Число порций — целочисленное деление вниз. Фронт только форматирует (`1200 g` → «1,2 кг»). [ПРЕДПОЛОЖЕНО: пересчёт г↔мл по плотности не нужен]
- При старте сервис проверяет и иначе не запускается: у каждого продукта из рецептов есть единица и справочная цена > 0; рецепт каждого блюда непуст; каждая норма > 0; `n0 > 0`; `OPEN_AT < CLOSE_AT` (работа через полночь не поддерживается); зона ресторана загружается.

### 2.3 Заказы и протокол блокировок
**Протокол (обязателен для всех писателей `batches`: заказ, поставка, «дворник», прыжок времени; единственное исключение — сброс, см. 2.8):** первой операцией над складом транзакция блокирует затронутые продукты `SELECT … FOR UPDATE` **по одному, циклом по отсортированному списку id**; только после этого читает часы и партии. Остаток пишется относительно: `UPDATE batches SET remaining = remaining − $x WHERE id = $id AND remaining >= $x`; 0 затронутых строк — нарушение протокола: откат и `500`, не `409`. Страховка в БД: `CHECK (remaining >= 0)`. [ПРОВЕРЕНО: без общего правила — потеря обновления и дедлок, `r1_B` эксп. 1.2, 1.3]

Заказ:
1. До транзакции: валидация (неизвестное блюдо, пустой заказ, одно блюдо в двух строках, порции вне 1…10000 — `400`, ничего не записано); суммирование потребности по всем блюдам заказа проверенной арифметикой. Блюда и рецепты неизменны (только сид), поэтому проверка до транзакции безопасна.
2. Транзакция. Первая команда — `INSERT INTO orders (id, body_hash, …) ON CONFLICT (id) DO NOTHING`. Хэш тела — от `id` и позиций `(dish_id, порции)`, отсортированных по `dish_id`. Вставлено 0 строк → читаем сохранённый заказ: хэш совпал — отдаём сохранённое тело ответа с `replayed: true` (код `200` для принятого, `409 insufficient_stock` для отклонённого); не совпал — `409 order_conflict`.
3. Блокировка продуктов из суммарной потребности по протоколу.
4. `now = clock.Now()` — после блокировок; это время заказа.
5. Чтение партий с `remaining > 0 AND expires_at > now`. Чистая функция `domain.PlanWriteoff(потребность, партии)` строит план FEFO по `(expires_at, batch_id)` либо возвращает нехватку.
6. Хватает → относительные `UPDATE`, движения `sale`, статус `accepted`, `201` с перечнем «партия — количество». Не хватает → партии не тронуты, заказ фиксируется со статусом `rejected` и перечнем `{product, нужно, доступно, не хватает}`, ответ `409 insufficient_stock`. Транзакция в обоих случаях коммитится.
- Отклонённые заказы показываются отдельно от созданных. «Расход» — это только движения `sale`; отклонённые заказы в него не входят, но входят в оценку спроса (2.6).
- Повтор отклонённого заказа с тем же id остаётся отказом: новая попытка — новый id; форма заказа создаёт id на каждое нажатие.
- Пул соединений — 20 (`DB_POOL_SIZE`); запросы сверх пула ждут соединения до 5 с, затем `503`. 50 параллельных заказов сторожа и 10 параллельных заказов демо проходят через эту очередь без ошибок. [НАДЕЮСЬ: 50 параллельных заказов проходят без двойной продажи — закрывается тестом-сторожем на настоящей БД]

### 2.4 Время, просрочка, сигналы
- Все моменты — `timestamptz` (UTC), на проводе RFC 3339. Зона ресторана — IANA-имя в `RESTAURANT_TZ`, проверяется при старте, `time/tzdata` вшита в бинарь. [ПРОВЕРЕНО: `r1_B` эксп. 2] Тесты границы дня — Europe/Moscow и Europe/Berlin; зоны с переводом часов в полночь не поддерживаются, это записано в README.
- Граница строгая: партия доступна, пока `now < expires_at`.
- **Часы.** Режимы: реальные, фиксированные (тесты), ускоренные. Состояние ускоренных — строка в БД `(sim_base, wall_base, speed)`; `now = sim_base + прошедшее × speed`, где прошедшее внутри процесса меряется монотонным временем. Смена скорости и прыжок сериализованы (мьютекс процесса + `FOR UPDATE` строки) и перебазируют обе точки; пауза = скорость 0. Прыжок задаётся интервалом `hours`, `0 < hours ≤ 720`; иное — `400`. Каждый прыжок пишется в журнал прыжков. Текущее симулированное время сохраняется не реже раза в 5 с. После рестарта: `sim_base = max(сохранённое время, max(movements.at), max(orders.at), max(batches.received_at))`, простой процесса не засчитывается.
- Корректность не зависит от фона: просрочка исключается предикатом в каждом запросе. **«Дворник»** будится на ближайший момент истечения или перехода в «истекает» и при любой смене часов; минимальный реальный интервал между проходами — 200 мс. Проход: блокировка продуктов по протоколу → одним запросом на множество обнуляет просроченные партии и пишет движения `writeoff`/`expired` с временем `= expires_at` → одно SSE-событие. Прыжок времени выполняет проход синхронно. [ПРОВЕРЕНО: 20 000 партий — 127 мс, `r2_B` 4г]
- **Порог «истекает»:** `t_ост < min(max(20% срока, 12 ч), 50% срока)`, срок = `expires_at − received_at`.
- **Сигнал.** Список истекающих партий — производная, считается при чтении (лента предупреждений, счётчик в шапке). Событие `batch.expiring` шлётся один раз на партию: `batches.expiring_notified_at` пишет проход «дворника» в той же транзакции под протоколом блокировок. Если партия из-за прыжка стала просроченной, минуя «истекает», `batch.expiring` для неё не шлётся — только `batch.expired`. `00_case.md:80`.
- Каждый ответ API содержит заголовок `X-Stand-Time`; время стенда и скорость видны на каждом экране.

### 2.5 Стоп-лист
Блюдо в стоп-листе ⇔ `min по ингредиентам floor(доступно / норма) = 0`. Считается при чтении; в ответе — причина (какого продукта сколько не хватает на одну порцию) и «порций доступно» для остальных блюд. Обновление на экране — по SSE после поставки, заказа, истечения. Доп. (первый кандидат на отсечение): прогноз момента попадания в стоп-лист.

### 2.6 Спрос, мониторинг, предложение поставок
- **Часы работы** ресторана — `OPEN_AT`, `CLOSE_AT` в конфиге; `W(a, b)` — рабочие часы в интервале (чистая функция, дробное число).
- **Оценка спроса** блюда, порций в день: `λ_d = (prior_d × n0 + запрошено_d) / (n0 + активные_дни)`. `prior_d` — априорный дневной спрос из сида; `запрошено_d` — порции в принятых и отклонённых заказах за окно `N` календарных суток; `активные_дни` — длина окна в календарных сутках (дробное число) минус интервалы, пропущенные прыжками времени. `n0 > 0`. [ПРОВЕРЕНО по формуле: без поправки на прыжок λ падает до 18 % априорной, `r2_B` 4д]
- **Ожидаемая потребность** в продукте: `rate_p_день = Σ_d λ_d × норма_dp`; `rate_p_час = rate_p_день / W_день`, где `W_день = CLOSE_AT − OPEN_AT` в часах. В проекции риска и в предохранителе Bg используется `rate_p_час`, в предложении поставок — `rate_p_день`. Это оценка (float), не остаток.
- **Количество под риском** партии — проекция FEFO: по партиям продукта в порядке `(expires_at, id)`: `cap = rate_p_час × W(now, e_b) − used`, `use = min(remaining_b, max(cap, 0))`, `risk_b = remaining_b − use`, `used += use`. Партия с `W(now, e_b) < W_min` (`HOT_W_MIN_HOURS`, 0,5 ч) — «обречённая»: в проекцию не входит (`use = 0`), `risk_b = remaining_b`, в рекомендациях не участвует, видна только в ленте предупреждений.
- **Мониторинг:** остатки по продуктам и по партиям, оставшееся время, статус партии `ok | expiring | expired`, лента предупреждений.
- **Предложение необходимых поставок** (`00_case.md:82`) — для продуктов, входящих хотя бы в один рецепт:
  - `пригодный_запас_p = Σ (remaining_b − risk_b)`;
  - `к заказу = max(0, rate_p_день × (срок доставки + дни покрытия) − пригодный запас)`, вверх до кратного упаковке; если `rate_p_день = 0` — минимальный запас: `MIN_PORTIONS × наибольшая норма этого продукта среди блюд − пригодный запас`, не меньше 0;
  - `дата обнуления = now + пригодный_запас / rate_p_день` суток; при `rate_p_день = 0` — не указывается;
  - срочность: `now` — продукт блокирует блюдо из стоп-листа или обнулится раньше срока доставки; `soon` — обнулится раньше `срок доставки + дни покрытия`; иначе `planned`;
  - строки с `к заказу = 0` не показываются; порядок: блокирующие блюда из стоп-листа, затем по дате обнуления, затем по id;
  - объяснение текстом с числами.
  Значения по умолчанию: срок доставки 1 сутки, упаковка 1 базовая единица (поля продукта), дни покрытия 3, `MIN_PORTIONS` 10, `N` 14, `n0` 3, `OPEN_AT` 10:00, `CLOSE_AT` 23:00 — все в конфиге. [ПРЕДПОЛОЖЕНО: значения по умолчанию разумны для демо]

### 2.7 Горячие предложения
Оба алгоритма — чистые функции `(снимок, рецепты, цены, расписание, спрос, now) → []Offer`; блюда из стоп-листа исключены; в объяснении — продукт, партия, количество, рабочих часов до срока; порядок детерминирован. Справочная закупочная цена продукта `price_p` — поле сида; в кейсе цены нет, это наше допущение, записанное в README.

**`hotoffers/a` — R, «требуемый темп»** (не использует прогноз спроса).
1. Партии продукта — по `(expires_at, id)`; обречённые пропускаются.
2. `need_p = price_p × max_b (Σ remaining партий до b включительно / W(now, e_b))`; партия, давшая максимум, — опорная для объяснения.
3. `share_dp = норма_dp / Σ_d' норма_d'p` по всем блюдам меню с этим продуктом, включая стоящие в стоп-листе.
4. `priority(d) = Σ_p need_p × share_dp`; исключаются блюда из стоп-листа и с нулевым приоритетом; в список идут первые `HOT_TOP_N` (по умолчанию 3). Цели в порциях у R нет.
5. Порядок: приоритет по убыванию (округление до 6 значащих цифр), затем более ранний срок опорной партии, затем id блюда.
Срок стоит в знаменателе: при прочих равных меньше времени → выше приоритет. Это буква `00_case.md:89-91`.

**`hotoffers/b` — Bg, «жадное распределение с предохранителем»** (использует `risk` из 2.6).
1. `risk_p = Σ risk_b` по необречённым партиям; `e*_p` — срок первой необречённой партии с `risk_b > 0` (определён только при `risk_p > 0`).
2. Предохранитель: блюдо исключается, если у него есть ингредиент с `risk_p = 0`, `rate_p_час > 0` и `остаток_p < HOT_COVER_HOURS × rate_p_час` (12 рабочих часов, конфиг). Причина исключения возвращается.
3. Цикл: `v_p = остаток_p` — все доступные партии продукта, включая обречённые. Среди неисключённых блюд не из стоп-листа, у которых `v_p ≥ норма_dp` по всем ингредиентам: `gain(d) = Σ price_p × min(норма_dp, risk_p) / W(now, e*_p)` по ингредиентам с `risk_p > 0` — спасённая стоимость в рабочий час до срока. Берётся максимум при `gain > 0` (сравнение после округления до 6 значащих цифр); при равенстве — раньше `min e*_p`, затем id блюда. Затем `v_p −= норма`, `risk_p = max(0, risk_p − норма)`, цель блюда +1. Стоп: нет блюда с `gain > 0` либо достигнут предел итераций `HOT_MAX_ITER` (200).
4. Выход: первые `HOT_TOP_N` блюд в порядке первого выбора, цель в порциях рядом с обычным темпом продаж, по каждому рисковому ингредиенту — партия, количество под риском, рабочих часов до срока.
Монотонность по сроку (при прочих равных уменьшение времени до срока не понижает ранг блюда) закрепляется property-тестом для обоих алгоритмов. [ПРОВЕРЕНО на макете: вес по сроку не меняет списания, `r2_C` спор 4]

**Сравнение (`cmd/simulator bench`)** — чистый домен в памяти, общие seed, парная разность.
- Спрос — пуассоновский по рабочим часам с дневным профилем. Две модели влияния рекомендации: M1 — множитель `u` на спрос блюда; M2 — число гостей фиксировано, рекомендация меняет только вес блюда при выборе. Размер списка `k = HOT_TOP_N = 3`; подъём убывает с позицией: `u_i = 1 + (u − 1) / i` для позиции `i = 1…k`; каждый сценарий содержит больше `k` блюд с рисковыми ингредиентами.
- Алгоритмы видят только историю заказов, не параметры генератора; заказы на горячие блюда помечаются.
- Контроли: C0 без рекомендаций, RND случайные, POP популярные, C1 по ближайшему сроку. Эффект алгоритма считается от RND.
- Пять сценариев: скоропорт в трёх блюдах; избыточная поставка; блюдо с двумя рисковыми ингредиентами; рисковый продукт с дефицитным попутчиком; дешёвая зелень против дорогого продукта.
- Метрики: стоимость списаний и доля списанного от поступившего (основные), отказы в заказах (ограничение), списания по количеству.
- 200 seed; основная точка — M2, `u = 1.5`, фиксируется до прогона; на `u = 1.2` и `2.0` проверяется только знак.
- **Правило победителя.** Ограничение: отказы не больше +1 % заказов к C0 **во всех клетках обеих моделей**; нарушитель основным не становится. Списания R и Bg сравниваются между собой в основной точке, по сценариям: в сценарии ничья, если 95 % интервал парной разности включает 0 либо разница меньше 5 % списаний C0 в этом сценарии; победа — лучше в ≥ 4 сценариях из 5 и не хуже ни в одном; если победы нет ни у одного — ничья. При ничьей основным становится прошедший ограничение; если прошли оба — R; если не прошёл ни один — основным идёт R, утверждений о сравнении нет. Цифра для экрана и README — снижение списаний основного алгоритма относительно RND и относительно C1 (база порогов правила — C0, база показываемого эффекта — RND; это разные числа, и оба названы).
- **Граница.** Результат — к концу дня 4. Готов — одна цифра на экране аналитики и таблица в README. Не готов — основным идёт R, цифры на экране и утверждений о сравнении в демо и README нет.
- [НАДЕЮСЬ: подъём спроса от рекомендации существует; его величина выдумана, поэтому в README утверждается только направление эффекта] [НАДЕЮСЬ: вывод о победителе в нашем bench совпадёт с макетом Альтернативщика]

Обновление списка: пересчёт при каждом чтении. SSE `hotoffers.changed` шлётся по событиям склада и по тику (каждые 60 с времени стенда, но не чаще раза в 1 с реального времени), только если изменился отпечаток списка. Отпечаток живёт в памяти процесса, служит лишь для подавления лишних событий и на ответ чтения не влияет; сохраняемого состояния списка нет.

### 2.8 Интерфейс, стенд, развёртывание
- Экраны по `frontend-prompt.md`: Склад, Меню и стоп-лист, Горячие предложения, Поставки и предложение поставок, Заказы, Демо-панель, Аналитика (списания, дефицит; одна цифра сравнения — если bench готов к концу дня 4). В шапке каждого экрана — время стенда, скорость, счётчик предупреждений, индикатор связи.
- SSE-события — сигналы «перечитай»; фронт перезапрашивает данные.
- **Сид** задаётся относительно `T0` — 11:00 по времени ресторана в календарный день сброса: справочники, цены, априорный спрос, 14 дней истории заказов и поставок, сгенерированной симулятором с фиксированным seed. Сид пишет `received_at` партий и время заказов в прошлом напрямую, минуя API, — единственное исключение из `received_at = clock.Now()`. Сид загружается при первом старте на пустой БД и при каждом сбросе.
- **Сброс** — под затвором процесса (`RWMutex`: все изменяющие запросы и «дворник» берут его на чтение, сброс — на запись). Затвор заменяет блокировку продуктов: пока он взят на запись, других писателей нет. Внутри — `DELETE` (не `TRUNCATE`), загрузка сида, перебазирование часов на `T0`, скорость ×1, симулятор остановлен. Тест: после сброса стоп-лист и горячие предложения равны эталону. [ПРОВЕРЕНО: `TRUNCATE` даёт дедлок с заказом, `r2_B` 4а]
- Генератор событий — пакет, общий для `cmd/simulator` (bench и работа против API по HTTP) и для демо-панели. На стенде симулятор идёт постоянно.
- Токен `DEMO_TOKEN` закрывает только сброс, прыжок и смену скорости; без него эти кнопки скрыты. Всё остальное, включая запуск и паузу симулятора, открыто. Токен — в сопроводительной записке для жюри.
- Развёртывание: `docker compose` на VPS, ссылка для жюри; код на GitHub.

## 3. Что показываем (5 минут)
1. Симулятор уже идёт: остатки убывают, партии желтеют. Пауза.
2. Сигнал «истекает» по партии → карточка горячего предложения с партией и целью в порциях.
3. Заказ из двух блюд с общим ингредиентом: списание по FEFO с перечнем партий.
4. 10 параллельных заказов на последние 3 порции: ровно 3 успеха, 7 отказов с причиной, остаток 0.
5. Прыжок времени: списание в журнале → блюдо в стоп-листе с причиной → этот продукт первым в предложении поставок.
6. Принимаем поставку: блюдо вернулось в меню; повторная отправка — «уже принята», остаток тот же.
7. Если bench готов к концу дня 4 — одна цифра: на сколько основной алгоритм снижает списания против случайных рекомендаций. Иначе — график списаний по причинам, без утверждений о сравнении.

## 4. Что взято из второго решения (01b) и что отброшено
Взято: идемпотентность заказа по ключу; журнал движений (аудит и источник статистики; доступность определяет `batches.remaining`, сверка — тестом-сторожем); излишек `max(0, остаток − прогноз потребления)` — совпал с «количеством под риском» из 01a; стабильная сортировка и top-N.
Отброшено: подписчик, пересчитывающий доступность и рекомендации в сохранённое состояние, — производные считаются при чтении; справочники с CRUD — сид и автосоздание из поставки; блокировка строк партий — заменена блокировкой продуктов (2.3); подписи экранов под роли — авторизации нет, подписи без неё ничего не дают.
Снято по итогам дебата: алгоритм A из первой редакции; база срока `created_at`; отдельный экран «A против B»; гистерезис списка рекомендаций.

## 5. Решения по неоднозначностям (`main-prompt.md`)
| Вопрос | Решение | Почему |
|---|---|---|
| Срок хранения | **Оставляем**: `expires_at = received_at + длительность`, абсолютная дата — как есть. **Уточняем**: `received_at` — время стенда в момент приёма, `created_at` в расчёт не входит | Запрос с реальной датой работает при любом времени стенда |
| Единицы | **Оставляем** `int64` в `g/ml/pcs`. **Добавляем**: вход — строка + единица, собственный разбор, проверенная арифметика, пределы | `ParseFloat` принимает `1e3`, `int64` молча оборачивается |
| Заказ | **Оставляем**: отказ целиком с перечнем нехватки. **Добавляем**: идемпотентность по id, `409 order_conflict`, отказ хранится как `rejected` | Повтор после таймаута не списывает дважды |
| Списание | **Оставляем**: строгий FEFO, при равенстве срока — по id партии. **Добавляем**: протокол блокировок для всех писателей партий | Иначе «дворник» оживляет просроченную партию |
| Порог «истекает» | **Меняем**: `t_ост < min(max(20% срока, 12 ч), 50% срока)` | Без верхней границы продукт со сроком 10 ч «истекает» с момента приёма |
| Часовой пояс | **Оставляем**: одна зона в конфиге, «годен до даты» — до начала следующего локального дня. **Ограничиваем**: зоны с переводом часов в полночь не поддерживаются | `time.Date` в такой зоне сдвигает границу на час |
| Просроченные партии | **Оставляем** событие списания с причиной. **Уточняем**: доступность определяет предикат времени, а не событие; время события = `expires_at` | Стоп-лист верен, даже если фон не успел |
| Время | **Оставляем**: в домене нет `time.Now()`. **Добавляем**: сериализованная смена часов, монотонность, продолжение после рестарта без засчёта простоя | Рестарт не оживляет партии и не устраивает лавину просрочек |
