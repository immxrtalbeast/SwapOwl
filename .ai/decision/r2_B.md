# r2_B — Скептик, финал

Прочитаны r1_A, r1_B, r1_C, r1_author. Эксперименты: postgres:16.15 в docker, Go 1.25.3.

## 1. Вердикт: KEEP WITH CHANGES
Архитектура (партии + предикат времени + блокировка продуктов + чистые функции) выдержала атаку; автор принял все мои существенные претензии и честно снял формулу A. PIVOT не оправдан: переделка стоила бы дней, выигрыш по критериям жюри не очевиден. Остались дыры в НОВЫХ механизмах автора (п. 4).

## 2. Топ-3 обязательных изменения
1. **Сброс/прыжок/дворник не должны брать блокировку таблицы `orders` после блокировки продуктов.** Заказ теперь первым делает `INSERT orders`, затем берёт продукты; `TRUNCATE orders` в сбросе после `FOR UPDATE` продуктов даёт дедлок (п. 4а). Сброс — `DELETE`, либо блокировка в одном порядке «orders, затем продукты».
2. **Оценка спроса `λ` должна переживать прыжок времени** (п. 4д): окно N дней после прыжка пусто, `λ` падает к нулю, «риск» растёт, горячие и поставки вырождаются ровно в момент демо. Окно считать по «активному» времени либо прыжок синтезирует спрос по prior; тест «до/после прыжка».
3. **Часы: сериализовать смену и хранить монотонную часть** (п. 4в): `SELECT … FOR UPDATE` строки часов при перебазировании; `now` внутри процесса — `base + monotonic elapsed × speed`, а не разность двух wall-значений; простой на рестарте — явная политика (пауза или засчёт).

## 4. Новые находки по механизмам автора
**(а) `INSERT orders` первым + цикл блокировок продуктов.**
- **P1 [ПРОВЕРЕНО] Дедлок со сбросом.** Вход: идущий симулятор, жмут «сброс». Путь: сброс блокирует продукт 1 и выполняет `TRUNCATE orders`; заказ уже вставил строку в `orders` (RowExclusive) и ждёт продукт 1. Результат: `deadlock detected` (процесс сброса ждёт AccessExclusive на `orders`, заказ — блокировку строки продукта); один из них убит — у заказа 500 или сброс не выполнен. С `DELETE FROM orders` дедлока нет. Демо-режим, но сброс — часть сценария показа.
- Корректно [ПРОВЕРЕНО]: повторный id ждёт на уникальном индексе, держа только блокировку строки заказа без блокировок продуктов, поэтому цикла нет; фиксация `rejected` без отката безопасна, пока план строится до записи.
- P2 [ГИПОТЕЗА]: одновременные заказы на «соль/масло» (общий ингредиент) сериализуются; блокировка держится до конца транзакции вместе с записью `rejected` и ответом. Не мерил; на масштабе жюри несущественно. Пул соединений: ожидающие заказы держат соединения, сброс/прыжок/дворник могут остаться без свободного — размер пула > числа параллельных запросов демо.

**(б) `received_at = clock.Now()`.**
- P2 [ГИПОТЕЗА]: `received_at` поставки читать после блокировок продуктов, как и `now` заказа (автор распространил правило только на заказ). Иначе поставка, ждавшая прыжок времени, получает `received_at` до прыжка и при коротком сроке принимается уже просроченной без предупреждения.
- Корректно: срок от `received_at` + `ускоренные часы` даёт предсказуемую жизнь партии (72 ч при ×3600 = 72 с); повтор поставки возвращает сохранённое.

**(в) Часы `(sim_base, wall_base, speed)`.**
- **P1 [ГИПОТЕЗА, механизм очевиден]** Две одновременные смены скорости: чтение-изменение-запись без `FOR UPDATE` строки часов — потерянное обновление, итог зависит от порядка коммитов (оба считают `sim_base` по своему прочитанному состоянию). Исправить блокировкой строки часов или мьютексом процесса (один экземпляр).
- P1 [ГИПОТЕЗА]: `wall_base` хранится в БД как wall-время; при шаге системных часов назад (NTP, VPS) `now` идёт назад → перекос порядка событий, мигание стоп-листа (дворник уже обнулил, но предикаты и время движений расходятся). Внутри процесса использовать монотонную часть (`time.Since` по `time.Time` с monotonic), в БД писать только при перебазировании.
- P2 [ГИПОТЕЗА]: простой процесса засчитывается в симулированное время ×speed (10 мин простоя при ×3600 — 25 суток): после рестарта пачка просрочек. Выбрать явно: пауза при старте или засчёт.
- Рестарт без потери состояния — механизм корректен.

**(г) Дворник на истечение и на «истекает».**
- Опровергнуто как проблема [ПРОВЕРЕНО]: set-based списание 20 000 партий × 60 продуктов под блокировкой всех продуктов — 127 мс (`UPDATE … RETURNING` + `INSERT … SELECT`), заказы ждут доли секунды. Условие: списание одним запросом, не циклом по партиям; движения датировать `expires_at`.
- P2 [ГИПОТЕЗА]: при больших скоростях сон до ближайшего события короче времени обработки — нужен минимальный реальный интервал и пробуждение по смене часов (канал), иначе занятый цикл; SSE после большого прыжка — одно событие «пересчитай», а не тысяча.

**(д) `λ = (prior·n0 + продано)/(n0 + дни)`.**
- **P1 [ГИПОТЕЗА, следует из формулы]** После прыжка времени окно последних N дней не содержит продаж (никто не заказывал в пропущенный интервал), `λ → prior·n0/(n0+N)` (при n0=3, N=14 — 18% prior), «количество под риском» = остаток − λ·t_ост растёт, горячие и предложение поставок сдвигаются в момент демо прыжка. Исправление — п. 2.2 выше.
- Размерность корректна (продано — штуки за `дни` дней, prior — штуки/день). Корректно для холодного старта.
- P2: спрос, цензурированный стоп-листом (блюдо недоступно — продаж нет), занижает λ именно для дефицитных блюд; решение уже учитывает отказы в 2.6, распространить на оценку для горячих.

**(е) `UPDATE … SET remaining = remaining - $x WHERE remaining >= $x`.**
- Корректно [ПРОВЕРЕНО в r1 на 1.2/1.3 механике]: под блокировкой продукта план не пересекается с другими писателями, 0 строк означает баг, а не штатный отказ → откат и 500; не маскировать как `409`.

## 5. Держу ли я [ПРОВЕРЕННЫЙ] P0, не опровергнутый автором
**Нет.** Дедлок сброс/заказ (4а) — [ПРОВЕРЕНО], но P1: затрагивает демо-режим, чинится заменой `TRUNCATE` на `DELETE`; кейс не ломает. Остальное — P1/P2.
