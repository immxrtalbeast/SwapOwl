# r1_C — Агент C, «Альтернативщик»

## 0. Как решил бы я (написано до чтения 01_solution.md, после не редактировалось)

1. Архитектура: один Go-бинарник (модульный монолит: supply / orders / stock / hot / sim) + PostgreSQL + React SPA; никаких брокеров и микросервисов. Генератор событий — тот же бинарник в режиме `sim`, бьёт в публичный HTTP API. SSE (не WebSocket) для пуша остатков/стоп-листа/горячих. Деплой — docker-compose на одной VPS.
2. Данные: `product`, `batch(product_id, qty_left, expires_at, supply_id)`, `dish`, `recipe(dish_id, product_id, qty)`, `order`, `order_item`, журнал движений `stock_move(batch_id, delta, reason)` — остаток всегда выводим из журнала, списания (заказ/просрочка) различимы по `reason`.
3. Конкурентность: заказ — одна транзакция; `SELECT ... FOR UPDATE` по партиям нужных продуктов в фиксированном порядке `product_id, expires_at, id` (нет дедлоков), FEFO-списание, при нехватке — откат и 409 со списком недостающего. Идемпотентность поставок по уникальному id поставки. Нагрузка ресторана мала — оптимистичные схемы и кэши не нужны.
4. Стоп-лист — производная функция от остатков (max порций блюда = min по ингредиентам floor(годный остаток / норма)), пересчитывается после каждой транзакции, а не хранится как отдельное состояние. Просрочка — по `expires_at <= now` в запросе плюс фоновый тикер, который пишет движение `expired`.
5. Горячие предложения — НЕ взвешенная сумма признаков, а оценка в единицах результата: «сколько продукта будет списано, если ничего не делать». Для каждой партии: прогноз расхода до срока (скорость продаж блюд × нормы) → ожидаемый излишек `surplus_p = max(0, остаток_до_срока − прогноз_расхода)`, с FEFO-каскадом по партиям. Приоритет блюда = сколько излишка (в рублях/граммах) спасает одна доп. порция, суммарно по ингредиентам, с ограничением «не съедать дефицитный ингредиент» (штраф за ингредиент, у которого прогнозируется стоп-лист раньше поставки).
6. Список формируется жадно с пересчётом: взял лучшее блюдо, виртуально «продал» k порций, пересчитал излишки — так один и тот же излишек не рекламируется пятью блюдами, а продукт, используемый в нескольких блюдах, получает ровно столько витрины, сколько нужно. Объяснение — из тех же чисел: «Сливки, партия №12: истекает через 9 ч, остаток 4 л, обычный расход до срока 1,5 л → 2,5 л под списание; блюдо расходует 0,2 л/порция».
7. Запасной (базовый) вариант — простая срочность `max по ингредиентам (1/время_до_срока)`; его держу как контроль в симуляторе.
8. Доказательство качества: симулятор с общим seed, парное сравнение «без рекомендаций / наивная срочность / мой алгоритм» по списаниям, отказам и выручке; график на дашборде аналитики.
9. Сроки: д1 — схема, контракты API, каркас; д2–3 — поставки/заказы/FEFO/стоп-лист + тесты гонок; д4 — горячие + симулятор; д5 — UI, SSE, аналитика; д6 — деплой, нагрузочный прогон, полировка; д7 — заморозка, демо-сценарий, видео.

## 2. Алгоритмы

Обозначения: `risk_b` — количество под риском партии (проекция FEFO, как в 2.7), `норма_dp` — расход продукта p на порцию блюда d, `цена_p` — закупочная цена.

**R — «требуемый темп» (без прогноза спроса).** Для продукта: `need_p = цена_p × max по партиям (Σ остатков партий со сроком ≤ e_b) / рабочие_часы_до(e_b)` — сколько рублей в час нужно продавать, чтобы ничего не истекло. `priority(d) = Σ_p need_p × норма_dp / Σ_d' норма_d'p`. Сложность O(партии + строки рецептов). Вход: партии, рецепты, цены, часы работы; история спроса не нужна. Объяснение: «Тунец: 5,2 кг, до срока 14 рабочих часов — нужно 370 г/ч; порция расходует 180 г». Пункты кейса: срок — знаменатель; остаток — числитель; норма — доля блюда; несколько блюд — темп делится между блюдами пропорционально норме, а не поровну. Плох тем, что не знает, справится ли обычный спрос: рекомендует всегда, даже когда риска нет (отказы при M1: +132 на прогон в S1).

**Bg — жадное распределение с предохранителем** (B из 2.7 плюс одно правило). Перед жадным циклом исключаются блюда, у которых есть ингредиент без риска и с запасом меньше одного рабочего дня обычного расхода. Дальше как B: `gain(d) = Σ_p цена_p × min(норма_dp, risk_p)`, берём максимум, уменьшаем виртуальные остатки, повторяем. Сложность O(порции × блюда × ингредиенты). Вход: как у B. Объяснение: как у B плюс строка «Капрезе не предлагаем: помидоров осталось на 5 ч». Пункты кейса: срок и остаток — внутри `risk`; норма — в `gain`; несколько блюд — виртуальное списание не даёт рекламировать один излишек пятью блюдами. Плох тем, что нужен прогноз спроса (холодный старт, см. П5) и что предохранитель меняет списания на отказы (S4: −14 % списаний вместо −38 %).

**W — прогон «что-если»** (мой вариант из шага 0). Жадно по слотам: для каждого блюда-кандидата почасовая проекция склада на 72 ч со спросом `λ̂ × 1.5` у кандидата; `J = списания + β × потерянные продажи`; берём кандидата с наибольшим снижением J, иначе слот пуст. Сложность O(k × блюда × горизонт × блюда × ингредиенты) — в макете на порядок медленнее B. Вход: всё, что у B, плюс график плановых поставок и допущение о подъёме спроса. Объяснение — разность двух проекций: «без акции спишем 2,5 л сливок партии №12, с акцией 0,4 л». Все четыре пункта кейса учитываются неявно. Плох: без графика поставок рекомендует пустой список [ПРОВЕРЕНО: первая версия без поставок не выдала ни одной рекомендации]; зависит от выдуманного u; на симуляторе играет «дома», потому что устроен как сам симулятор.

**LP-оптимум — только как верхняя граница в bench** [ГИПОТЕЗА, не проверял]: максимум `Σ цена × спасено` при ограничениях по остаткам и по достижимым доп. порциям. В продукт не нужен; строка «B в пределах X % от оптимума» усилила бы защиту, но это P2.

Сопоставление с A и B из 2.7, снижение списаний относительно «без рекомендаций», u = 1.5, 200 seed, в скобках — изменение числа отказов на прогон (всего ~1250 заказов) [ПРОВЕРЕНО]:

## 3. Претензии

**П1 [P1][ПРОВЕРЕНО] Модель «top-k получают спрос ×u» меряет подъём спроса, а не алгоритм.** `01_solution.md` 2.7, «Сравнение на симуляторе». При этой модели (M1) случайные k блюд снижают списания на 21 / 42 / 49 % в S1 и на 53 / 89 / 99 % в S2 (u = 1.2 / 1.5 / 2.0); остальные (кроме A) дают 25–50 % и 69–100 %. При M2 случайный выбор даёт 0 ± 1 %, и алгоритмы расходятся. Знак меняется от модели: C1 в S5 — −17 % при M1 и +10 % при M2. Сделать: вторую модель спроса (M2) и два отрицательных контроля — RND и POP («самые популярные»; при M2 и u = 1.5 он увеличивает списания на 31–35 % в S2–S5); эффект алгоритма считать от RND, а не от C0.

**П2 [P1][ПРОВЕРЕНО] Правило победителя отдаёт победу бездействию.** 2.7: «меньшая стоимость списаний без роста отказов; при ничьей — A». В S1/M1/u=1.5 у B −45 % списаний и +89 отказов, у A −0,9 % и 0 отказов: по букве правила B выбывает, остаётся A. Порог «роста» и «ничьей» не задан. Сделать: отказы — условие с допуском (не больше +1 % заказов к C0); ничья — 95 % интервал парной разности включает 0 либо разница < 5 % списаний C0; победа — в ≥ 4 из 5 сценариев и не хуже ни в одном; основная клетка (M2, u = 1.5) фиксируется до прогона.

**П3 [P1][ПРОВЕРЕНО] Формула A.** (а) «Порог» в формуле не определён; с порогом «истекает» из раздела 5 срочность равна нулю почти всё рабочее время (продукт со сроком 48 ч получает окно 12 ч, которое приходится на ночь): −0…−1 % в S1, S4, S5, в S1 A в 100 % случаев рекомендует салат, а не блюда со сливками. (б) Поглощаемая доля — отношение, а не количество, плюс деление на число блюд: 20 г петрушки в одном блюде обгоняют тунец в трёх; в S5 A рекомендует картофель с зеленью в 100 % случаев, при M2 списания растут на 15 % (u = 1.5) и 28 % (u = 2.0). С порогом = полный срок (`Afull`) A оживает в S1, S2, S4, но в S5 остаётся +18 %. Сделать: A в этом виде не писать; вторым алгоритмом взять R либо умножать на `цена × риск` и убрать деление на число блюд.

**П4 [P1][ПРОВЕРЕНО] B не смотрит на нерисковые ингредиенты блюда.** 2.7, B. Продвигая блюдо, он выедает его обычные ингредиенты: S1/M1 +89 отказов на прогон при u = 1.5 и +165 при u = 2.0; критерий жюри «работа стоп-листа» при этом выглядит как сбой рекомендаций. Сделать: предохранитель Bg (5 строк), порог покрытия — в конфиге. Цена — см. S4 выше; при M2 выигрыш предохранителя мал, так что это страховка от худшего случая, а не бесплатное улучшение.

**П5 [P1][ПРОВЕРЕНО] Холодный старт.** 2.6 и 2.7 берут «средний расход за окно N дней»; на стенде после «сброса» (2.8) истории нет. При нулевом спросе в S1 B ставит первым стейк (говядина со сроком 240 ч), A и W выдают пустой список — экран горячих предложений на защите пуст или абсурден. Сделать: в сиде — априорный дневной спрос блюда, `λ̂ = (prior × n0 + продано) / (n0 + дни)`; до накопления истории показывать R.

**П6 [P1][ГИПОТЕЗА] Критерий весом в пятую часть оценки получает один день после контрольной точки.** Раздел 6: «День 5: горячие A и B, bench». Алгоритмы и bench — чистые функции без БД и API (`main-prompt.md:21`), их можно начать в день 2 отдельным исполнителем параллельно со складом; макет на ~300 строк пишется быстро, но прогон сетки занял больше 20 минут, а разбор результатов сдвинул мои собственные выводы. Сделать: bench и оба алгоритма — дни 2–4, день 5 — только экран и подключение.

**П7 [P2][ГИПОТЕЗА] Bench отдаёт алгоритмам истинный спрос.** Если `risk` считается по параметрам генератора, выигрывают алгоритмы с прогнозом. В макете спрос оценивался по наблюдённым заказам, включая поднятые рекомендацией, — это завышает «обычный» расход и занижает риск. Сделать: оценка только из истории; заказы на «горячие» блюда помечать и исключать либо учитывать с понижением.

**П8 [P2][ПРОВЕРЕНО] Списания можно снизить, потеряв деньги.** При M2 в S1 все алгоритмы снижают выручку (B: −13,5 тыс. при −2,9 тыс. списаний), потому что гостя переводят со стейка на пасту. В макете поставки фиксированы и остаток на конец не оценивался, так что размер эффекта преувеличен, но знак показателен. Сделать: третья метрика — маржа (выручка − себестоимость проданного − списания); в таблице показывать, не делая условием победы.

**П9 [P2][ГИПОТЕЗА] Порядок внутри top-k в bench не виден.** Подъём одинаков для всех k блюд; если k не меньше числа рисковых блюд, A и B дадут одно множество и «ничью». Сделать: подъём убывает с позицией, k меньше числа блюд с риском (в макете k = 1–2).

**П10 [P2][ГИПОТЕЗА] Упрощения вне 2.7 без потери баллов.** (а) 2.1: хэш канонизированного тела и `409 delivery_conflict` — достаточно PK и «уже принята». (б) 2.1: форма `expires_on` тянет часовой пояс, tzdata и правило конца дня; кейс (`00_case.md:26-27`) требует только «срок хранения» — оставить длительность, дату — если останется время. (в) Список рекомендаций будет мигать при каждом заказе (2.7 «пересчёт по событиям») — нужен гистерезис: блюдо держится в списке не меньше N минут. (г) Цель B «продать 12 порций до 18:00» может быть недостижима — показывать вместе с обычным темпом продаж.

## 4. Как сравнивать на симуляторе

- **Спрос.** Пуассоновский поток по часам с дневным профилем (обед, ужин). Две структурные модели: M1 — множитель u на спрос блюда; M2 — число гостей фиксировано, рекомендация меняет только вес блюда при выборе. Сетка u ∈ {1.2, 1.5, 2.0}; подъём убывает с позицией в списке.
- **Что делать с выдуманным влиянием.** Вывод принимается, только если знак устойчив по обеим моделям и всей сетке; алгоритм не должен знать u; отрицательные контроли калибруют, сколько эффекта даёт сам подъём. В README писать прямо: величина эффекта условна, проверяемо только направление. В продукте помечать заказы на «горячие» блюда, чтобы настоящий u можно было оценить позже.
- **Контроли.** C0 без рекомендаций, RND случайные, POP популярные, C1 по ближайшему сроку.
- **Метрики.** Основная — стоимость списаний, доля от поступившего. Ограничения: отказы (доля заказов), блюдо-часы в стоп-листе, маржа. Дополнительно — доля списаний по количеству.
- **Статистика.** ≥ 200 seed (в макете это дало интервал ±1–3 % от списаний C0), общие случайные числа, парная разность по seed, среднее и 95 % интервал. Параметры алгоритмов подбираются на одних seed, итог считается на других. Правило победителя и ничьей — из П2. Пример ничьей из макета: Bg − R в S3 = −20 ± 86 руб.
- **Обязательные сценарии.** Пять из таблицы раздела 2 плюс холодный старт (первые сутки без истории) и сдвиг спроса (прогноз построен на одном спросе, фактический другой) — последние два в макете не прогонялись.
