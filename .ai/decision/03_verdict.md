# 03 — Вердикт

## Итог: KEEP WITH CHANGES

Выведен по правилам шага 4 из `r2_A.md`, `r2_B.md`, `r2_C.md`, а не по мнению автора.

| Агент | Модель | Вердикт | [ПРОВЕРЕННЫЙ] P0 в финале |
|---|---|---|---|
| A, Аудитор требований | Opus | KEEP WITH CHANGES | нет (`r2_A.md` §4) |
| B, Скептик | Sonnet | KEEP WITH CHANGES | нет (`r2_B.md` §5) |
| C, Альтернативщик | Opus | KEEP WITH CHANGES | нет (`r2_C.md` §5) |

- Правило «2 из 3»: 3 из 3 за KEEP WITH CHANGES.
- Правило «проверенный P0 запрещает KEEP»: P0 не заявлен ни в одном раунде; KEEP без изменений никто и не выбрал.
- Правило «согласие в раунде 1 подозрительно»: согласия не было (30 претензий P1), а в раунде 2 Скептик отдельно атаковал новые механизмы автора и нашёл четыре P1 — все приняты ниже.
- Условие «нужен человек» (голоса 1-1-1 или неопровергнутый проверенный P0) не выполнено.

Архитектура (партии + журнал движений, доступность предикатом времени, производные при чтении, блокировка продуктов) осталась без изменений: Альтернативщик пришёл к ней же до чтения решения, Скептик подтвердил ядро экспериментами на PostgreSQL 16.

## Топ-3 проблемы
1. **Протокол блокировок был записан не для всех писателей партий.** «Дворник» без блокировки продукта оставлял `remaining = 2` у просроченной партии, а с обратным порядком — `deadlock detected` (`r1_B.md`, эксп. 1.2, 1.3); сброс через `TRUNCATE orders` — дедлок с заказом (`r2_B.md` 4а). Все три случая воспроизведены на БД.
2. **Алгоритм горячих предложений A и схема сравнения были негодны.** A почти ничего не делал в 3 сценариях из 5 и увеличивал списания в одном; модель «спрос ×u» награждала даже случайный выбор блюд, а правило победителя отдавало победу бездействию (`r1_C.md` П1–П3, макет на 200 seed).
3. **Время и история спроса на стенде.** База срока `created_at` ломала запрос жюри с реальной датой; пустая история после сброса и прыжок времени вырождали горячие предложения и предложение поставок ровно в момент демо (`r1_A.md` П2, П7; `r2_B.md` 4д; `r2_A.md` Д2).

## Принятые претензии (что меняем)

**Конкурентность**
- Любая транзакция, меняющая `batches` (заказ, поставка, дворник, прыжок, сброс), первой блокирует затронутые продукты в порядке id, циклом по отсортированному списку — `r1_B` зона 1, `r1_A` П8: воспроизведено экспериментом.
- Остаток пишется относительно: `remaining = remaining − x WHERE remaining >= x`; 0 строк — ошибка `500` и откат, не `409` — `r1_B`, `r2_B` 4е.
- `now` заказа и `received_at` поставки берутся из часов после получения блокировок — `r1_B`, `r2_B` 4б: при ×3600 секунда ожидания равна часу.
- Заказ: `INSERT … ON CONFLICT DO NOTHING` первой командой, хэш тела, `409 order_conflict`; отказ фиксируется как `rejected` без отката — `r1_B`: иначе два одновременных повтора списывают дважды.
- Сброс стенда: `DELETE`, не `TRUNCATE`, под общим затвором процесса — `r2_B` 4а: дедлок воспроизведён.
- «Дворник» списывает одним запросом на множество, имеет минимальный реальный интервал и будится сменой часов — `r2_B` 4г: 20 000 партий за 127 мс, но цикл по партиям и занятый цикл недопустимы.

**Время и сроки**
- `expires_at = received_at + длительность`, `received_at = clock.Now()`; `created_at` — только реквизит — `r1_B`, `r1_A` П7, Д6.
- Часы: состояние `(sim_base, wall_base, speed)`, смена сериализована, внутри процесса — монотонное время, отрицательный прыжок запрещён, после рестарта время продолжается с последней сохранённой точки, но не раньше последнего события; простой не засчитывается — `r1_B`, `r2_B` 4в.
- Сигнал «партия подходит к концу»: событие `batch.expiring`, лента предупреждений; факт уведомления хранится в партии — `r1_A` П1 (`00_case.md:80`), `r2_B`.
- Каждый ответ API несёт время стенда; поставка с `expires_on` в прошлом относительно стенда принимается с предупреждением — `r1_A` П7, `r2_C` спор 2.
- Утверждение «конец дня корректен при любой смене смещения» снято; зона проверяется при старте — `r1_B` эксп. 2.

**Единицы и поставки**
- Разбор количества по `^[0-9]+(\.[0-9]+)?$`, только строка; проверенная арифметика и верхние пределы — `r1_B` эксп. 3.
- `unit` необязателен для известного продукта; автосоздание — только с явным `unit`, через `ON CONFLICT DO NOTHING` — `r1_A` П9, `r1_B`.
- Хэш поставки — от нормализованной доменной структуры; две позиции одного продукта разрешены — `r1_B`.
- При старте проверяется, что у каждого продукта из рецептов есть единица и цена — `r2_C`.

**Горячие предложения**
- A в исходном виде снят. `hotoffers/a` = R «требуемый темп», `hotoffers/b` = Bg «жадное распределение с предохранителем»; полные определения — из `r2_C.md` §4 — `r1_C` П3, П4.
- В `gain` у Bg входит вес по сроку (спасённая стоимость в рабочий час до срока), монотонность закрепляется property-тестом — `r2_A` спор 4. Принято, потому что Альтернативщик проверил: строгий вес не меняет списания (расхождение 2 п. п. в одной клетке из десяти), то есть требование Аудитора ничего не стоит, а контрпример к букве кейса `00_case.md:89-91` убирает.
- Часы работы ресторана в конфиге, время до срока считается в рабочих часах; «обречённые» партии не продвигаются — `r2_C`: без этого теряется до трети эффекта.
- Справочная цена продукта — в сиде и в README как наше допущение — `r1_A` П3.
- Спрос: априорный в сиде + 14 дней истории; оценка учитывает и отклонённые заказы; время, пропущенное прыжком, в окно не входит — `r1_C` П5, `r1_A` П2, `r2_B` 4д.
- Bench: модели спроса M1 и M2, контроли C0/RND/POP/C1, подъём убывает с позицией, алгоритмы видят только историю; отказы проверяются по обеим моделям, нарушитель не может стать основным — `r1_C` П1, П2, П7, П9, `r2_C`.
- Граница bench: пять сценариев, результат к концу дня 4; не готов — основным идёт R, утверждений о сравнении в демо и README нет — `r2_A`, `r2_B`.

**Стенд, срок, демо**
- Сид задаётся относительно момента сброса, сброс перебазирует часы — `r2_A` Д2.
- Токен закрывает только сброс, прыжок и скорость; время стенда и идущий симулятор видны всем — `r1_A` П5, `r2_A` Д4.
- Отклонённые заказы отделены от созданных и не входят в расход — `r2_A` Д5.
- Алгоритмы и bench — дни 2–4; заполненная дизайн-система — условие выхода из дня 1 — `r1_A` П4, `r1_C` П6.
- Порядок демо — по Аудитору: идущий симулятор → сигнал → горячее → заказ → параллельные заказы → прыжок → поставка → повтор поставки → одна цифра — `r1_A` П6.
- Принятые правки сводятся в `.ai/solution.md`; противоречащие строки `backend-prompt.md` и чек-листа ревью исправляются в том же PR — `r2_A`.

## Отвергнутые претензии
- «Убрать хэш тела поставки и `409`» (`r1_C` П10а, `r1_A` П11) — без хэша поставка с другим содержимым получает «уже принята»; оба автора претензии сняли её в раунде 2.
- «Убрать `expires_on`» (`r1_C` П10б) — абсолютная дата уже правило проекта (`main-prompt.md:57,62`); снята автором претензии.
- «Продукты только из сида» (`r1_B`) — позиция поставки по кейсу несёт id и название; автосозданный продукт не входит в рецепты; Скептик понизил до P2.
- «A оставить основным по объяснимости» (`r1_B` §3) — формула A не определена при `t_ост > порог` и вредит в сценарии S5; против — и Аудитор, и Альтернативщик.
- «В A считать вклад по всем истекающим партиям» (`r1_A` П3) — это контроль C1, он слабее R и Bg; букву кейса закрывает R.
- «Сократить bench до 20 seed» (`r1_B` §3) — число seed — машинное время; режется объём сценариев и сетка `u`, а не seed. При этом мой довод «20 seed не отличат Bg от R» опровергнут Альтернативщиком — снимаю его.
- «Гистерезис списка рекомендаций» (`r1_C` П10в) — принят мной в раунде 1, **снят в финале**: это сохраняемое состояние производной и нарушение инварианта 6 (`r2_A` Д1).
