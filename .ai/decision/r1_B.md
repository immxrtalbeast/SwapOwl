# r1_B — Скептик: разбор 01_solution.md

Среда: Go 1.25.3, Docker (postgres:16.15); psql на хосте нет — гонял через `docker exec`. Эксперименты: `$TEMP/skeptic-exp` и ad-hoc SQL. Серьёзность: P0 не решает кейс / P1 потеря баллов / P2 улучшение. [ПРОВЕРЕНО] = источник или вывод эксперимента, [ГИПОТЕЗА] = нет. P0 не найдено: ни одна претензия не ломает кейс целиком, все исправимы правилами в решении.

## 1. Пять вероятных причин провала
1. **Дыра в протоколе блокировок (п. 2.3/2.4).** Корректность держится на «любой писатель партий берёт блокировку продукта», но дворник и прыжок времени (п. 2.4) этого не оговаривают. Без блокировки — потеря обновления, с обратным порядком — дедлок (эксп. 1.2, 1.3). Бьёт по критериям 1 и 4. [ПРОВЕРЕНО]
2. **Горячие предложения A/B стоят на выдуманном спросе и пустой истории.** На демо нет N дней расхода: «количество под риском» = весь остаток, все блюда «горячие»; бенч на собственной модели спроса с подъёмом `×u` подтверждает любой алгоритм. Критерий 3. [ГИПОТЕЗА]
3. **Перегруз объёма за 7 дней.** Два алгоритма + бенч (200 seed × сетка u) + предложение поставок с проекцией FEFO + SSE + часы в БД + аналитика + экран A/B + Playwright + VPS. День 4 («контрольная точка») несёт четыре крупные фичи. [ГИПОТЕЗА]
4. **Разбор входа и арифметика единиц отданы агентам без спецификации.** `ParseFloat` и `big.Rat` принимают `1e3`, `0x1p-2`, `1_0`, `.5`, `+3`; `int64` молча оборачивается при kg→g и порции×норма. Итог: неверное количество принято, склад в минус. [ПРОВЕРЕНО, эксп. 3]
5. **Время.** Три вида часов, `created_at` как база срока, `now` до ожидания блокировки, предикат vs событие списания: любое расхождение даёт стоп-лист, не совпадающий с остатками, прямо на демо «прыжка времени». [ПРОВЕРЕНО частично]

## 2. Четыре зоны

### Зона 1. Гонки
**Корректно (доказано).**
- `ORDER BY id FOR UPDATE` блокирует в порядке id. План `LockRows → Sort`; наблюдение: сессия B с `ANY('{c,a,b}')`, пока `b` держит A, уже держит `a` (nowait на `a` — ошибка) и не тронула `c` (nowait успешен). [ПРОВЕРЕНО, эксп. 1.1]. Порядок в документации не обещан (https://www.postgresql.org/docs/16/sql-select.html: «ORDER BY применяется первым, затем возможна блокировка»). Предостережение про «строки не по порядку» в READ COMMITTED касается изменения самого ключа сортировки; `products.id` не меняется — неприменимо. Остаточный риск — смена плана; страховка: блокировать циклом по отсортированному списку или тест на EXPLAIN.
- Идемпотентный повтор: второй `INSERT … ON CONFLICT DO NOTHING` ждёт первого, после коммита вставляет 0 строк, следующий `SELECT hash` видит `h1`; если первый откатился — второй вставляет. [ПРОВЕРЕНО, эксп. 1.4]. Механизм п. 2.1 корректен.
- В READ COMMITTED каждая команда берёт новый снимок, поэтому чтение партий (шаг 3) после ожидания блокировки видит коммиты предыдущего заказа (https://www.postgresql.org/docs/16/transaction-iso.html). Двойная продажа порции исключена, если ВСЕ писатели партий держат блокировку продукта.

**Претензии.**
- **P1 [ПРОВЕРЕНО] Дворник и потеря обновления.** Партии читаются без `FOR UPDATE`. Вход: заказ на 3 из остатка 5 + дворник по той же партии. Путь: заказ блокирует продукт, читает `remaining=5`; дворник (без блокировки продукта) ставит 0 и коммитит; заказ пишет `SET remaining = 5-3`. Результат: в БД `remaining=2` у просроченной партии (эксп. 1.2) — «ожившая» партия, нарушение инварианта 1. Если дворник идёт «партия → продукт» — `deadlock detected` (эксп. 1.3). Исправить: в п. 2.3/2.4 правило «любая транзакция, меняющая `batches`, первой берёт `FOR UPDATE` продуктов по порядку id»; писать `remaining = remaining - $x … WHERE remaining >= $x` и проверять число строк; тест-сторож «дворник + 50 заказов». Не P0: чинится одной строкой, но если исполнитель дворника правила не увидит, баг гарантирован.
- **P1 [ГИПОТЕЗА, логически следует из текста] `now` до ожидания блокировки.** Шаг 3: `now` «взят один раз в начале». Заказ ждёт блокировку, партия за это время истекла — списывается просроченное. Особенно при ускоренных часах: 2 с реального ожидания при ×3600 = 2 ч симулированных, партия со сроком 1 ч. Исправить: брать `now` из `clock` после получения блокировки.
- **P1 [ГИПОТЕЗА] Идемпотентность заказа.** Тот же id и другое тело для заказа не описано (для поставки — 409). Если «есть ли заказ с id» проверяется до транзакции (SELECT), два одновременных POST оба спишут. Исправить: `INSERT orders … ON CONFLICT DO NOTHING` первым в транзакции, сравнивать хэш тела, иначе 409.
- **P2 [ПРОВЕРЕНО]** Автосоздание продукта при двух одновременных первых поставках: простой `INSERT` второго падает `23505` (эксп. 1.4) → 500. Нужно `INSERT … ON CONFLICT DO NOTHING`, затем `FOR UPDATE`, затем сравнение единицы.
- **P2** `ANY($1)` вернёт меньше строк при неизвестном продукте — сверять число строк.

### Зона 2. Сроки и часовой пояс
- **Подтверждено.** Строгая граница `now < expires_at` согласуется с `main-prompt.md:49`. Допущение `tzdata` верно: в `scratch` и `alpine:3` без пакета `LoadLocation("Europe/Moscow")` даёт `unknown time zone`, с `import _ "time/tzdata"` работает (+0,4 МБ). [ПРОВЕРЕНО, эксп. 2]
- **P2 [ПРОВЕРЕНО] Полночь в зоне с переводом на 00:00.** `time.Date(y,m,d+1,0,0,0,0,loc)` для America/Sao_Paulo 4.11.2018 вернул 23:00 предыдущего дня (истинное начало дня — 01:00). Для зоны без перехода (Europe/Moscow, Berlin) — верно. Утверждение п. 5 «корректно при смене смещения» не доказано; зафиксировать зону в README, добавить тест на DST-зоне (Europe/Berlin, 30.03.2025) для обычного перехода в 02:00 (на полночь не влияет).
- **P1 [ГИПОТЕЗА] `created_at` как база срока.** Допущение п. 2.1 [ПРЕДПОЛОЖЕНО]. `created_at` в будущем → партия доступна для заказов до своего поступления (предиката `received_at <= now` нет), «оставшееся время» больше полного срока. `created_at` давно в прошлом / по реальному времени при ускоренных часах → партия «просрочена при приёме» и сразу списана. Без зоны → JSON-разбор `time.Time` вернёт ошибку (400). Исправить: `received_at = clock.Now()` при приёме; доступность `received_at <= now < expires_at`; окно допуска `created_at` с понятным 400.
- **P1 [ГИПОТЕЗА] Часы.** «Монотонность» заявлена без механизма: хранить `wall0, base, k` (не только смещение), запретить отрицательный прыжок в API, тест рестарта.
- **P2 Порог `min(max(20%,12 ч),50%)`.** Монотонен и ограничен (срок 10 ч → 5 ч; 48 ч → 12 ч; 100 ч → 20 ч) — корректен. Но `срочность = 1 − t_ост/порог` (п. 2.7) отрицательна при `t_ост > порога`; порог в п. 2.7 не определён. Обрезать `max(0,…)`.

### Зона 3. Единицы
- **P1 [ПРОВЕРЕНО] Разбор десятичной строки не специфицирован.** `ParseFloat`: `1e3`, `0x1p-2`, `1_0`, `Inf`, `NaN`, `.5`, `1.`, `+3` принимаются, `1,5` отвергается. `big.Rat.SetString`: плюс `1/3`, `1e400`. Исправить: свой разбор по `^[0-9]+(\.[0-9]+)?$` (ведущие нули ок; запятая, экспонента, знак — 400), таблица тестов из ~20 строк как контракт для исполнителя.
- **P1 [ПРОВЕРЕНО] Переполнение.** `q*1000` при `q=MaxInt64/1000+1` даёт отрицательное число без паники; `3e9 × 4e9` — то же (эксп. 3). «Переполнение → 400» в п. 2.2 не подкреплено проверенной арифметикой. Исправить: единый примитив с проверкой `a > Max/b` (или `bits.Mul64`) для разбора и для суммирования потребности + верхний предел количества.
- **P1 [ГИПОТЕЗА] Фиксация единицы по первой поставке.** Ошибочная первая поставка (`pcs` вместо `g`) навсегда делает корректные следующие `400`, исправить нечем. Исправить: единицы и продукты — из сида/рецептов, поставка неизвестного продукта → 400 (автосоздание убрать или ограничить).
- **P2 [ПРОВЕРЕНО]** JSON-число в `quantity` через `float64` теряет точность (`1.2345678901234568e+22`) — принимать только строку.

### Зона 4. Повторные поставки
- Тот же id + то же тело → replay; одновременные повторы; повтор после рестарта (состояние в БД) — механизм корректен (1.4).
- **P1 [ПРОВЕРЕНО] «Канонизированное тело» не определено.** Канонизация через `map[string]any` склеивает `1.50` и `1.5` (одинаковый хэш, эксп. 3), но теряет точность больших чисел и не сортирует позиции. Хэш сырых байтов даёт ложный 409 при другом порядке ключей. Исправить: хэш от доменной структуры после нормализации в базовые единицы (`1 kg` = `1000 g`), позиции отсортированы по `(product_id, срок, qty)`, `number`, `created_at` входят в хэш; хранить исходный ответ и отдавать его при replay.
- **P1 [ГИПОТЕЗА] Две позиции одного продукта в одной поставке.** Допустимо («позиция = партия»), но `UNIQUE(delivery_id, product_id)` у исполнителя даст 500 вместо приёма; разрешить явно и тестом. Блокировать уникальный отсортированный список продуктов.

## 3. Срок и модель спроса
- **Срок.** Ядро (поставки, заказы, стоп-лист, мониторинг) за дни 1–4 реалистично; дни 5–6 перегружены (A + B + бенч + аналитика + дизайн). Рекомендую: B делать только при готовом A; бенч сократить до 20 seed × 3 значения u для демо. [ГИПОТЕЗА]
- **Модель спроса.** Победитель определяется параметрами `u` и профилем, заданными авторами; интервал отражает шум seed, а не риск модели. Показать A/B на трёх профилях (равномерный, вечерний пик, «хит» одного блюда); A оставить основным по объяснимости (`00_case.md:100`). Холодный старт определить явно (равномерный спрос по рецептам). [ГИПОТЕЗА]
