# Якорная шкала

По каждому из пяти критериев жюри — как выглядит продукт на 3, 6 и 9 баллов. Якоря накопительные: 6 включает всё из 3, 9 — всё из 6. Балл ставится по наблюдению на запущенном стенде: экран, запрос и ответ, поведение. Промежуточные баллы (4–5, 7–8) — когда выполнена часть следующего якоря; 10 — девятка без единого замеченного дефекта.

## 1. Корректная работа со сроками годности и партиями

**3 балла**
- Отправленная через API поставка появляется на экране склада; остаток продукта вырос на её количество.
- Две поставки одного продукта видны как две отдельные партии, у каждой своя дата истечения.
- У партии показано оставшееся время хранения.

**6 баллов**
- Заказ списывает сначала партию с более ранним сроком; в ответе на заказ и на экране видно, из какой партии сколько списано.
- После наступления срока партия не участвует ни в остатке продукта, ни в заказах: заказ, которому хватало только с ней, получает отказ.
- Партии, срок которых подходит к концу, выделены цветом и собраны в ленту предупреждений со счётчиком.
- Повторная отправка той же поставки не меняет остатки; ответ сообщает, что поставка уже принята.
- Количество, введённое как `1.5 kg`, отображается как «1,5 кг» и даёт остаток 1500 г.

**9 баллов**
- При истечении партии без каких-либо других действий на открытом экране без перезагрузки появляется списание с причиной «истёк срок», а остаток уменьшается.
- Сигнал «партия подходит к концу» появляется на открытом экране в момент перехода, один раз на партию.
- Партия с пометкой «годен до 12 октября» доступна весь день 12 октября по времени ресторана и недоступна с первой секунды 13 октября.
- Та же поставка с тем же id, но другим содержимым отклоняется с понятной ошибкой; остатки не меняются.
- Некорректные количества (`1e3`, `-5`, `0`, `1,5`, `0.0005 kg`, дробные штуки, единица не той размерности) отклоняются с ошибкой, называющей причину; остатки не меняются.
- После перезапуска сервиса время стенда не ушло назад, просроченные партии остались просроченными.
- В журнале движений по любой партии: поступило − продано − списано = текущий остаток.

## 2. Работа стоп-листа при недостатке ингредиентов

**3 балла**
- Заказ на блюдо, для которого не хватает ингредиента, отклоняется.
- Есть экран со списком недоступных блюд.

**6 баллов**
- Блюдо попадает в стоп-лист сразу после заказа, израсходовавшего ингредиент, и выходит из него сразу после поставки — без ручных действий.
- У блюда в стоп-листе указана причина: какого продукта и сколько не хватает на порцию. У доступных блюд — сколько порций можно собрать.
- Заказ из двух блюд с общим ингредиентом, которого хватает на каждое по отдельности, но не на оба, отклоняется целиком; ни один остаток не изменился.
- Ответ на отклонённый заказ перечисляет недостающие продукты с количествами.

**9 баллов**
- Десять одновременных заказов на последние три порции: ровно три приняты, семь отклонены, остаток ингредиента равен нулю и нигде не отрицателен.
- Блюдо попадает в стоп-лист в момент истечения партии, когда других событий нет, — на открытом экране, без перезагрузки.
- Повторная отправка того же заказа (тот же id) не списывает продукты второй раз и возвращает тот же ответ.
- Отклонённые заказы видны отдельно от принятых и не уменьшают остатки.
- При потере связи с сервером экран показывает это явно; после восстановления стоп-лист актуален без перезагрузки.

## 3. Качество алгоритма формирования горячих предложений

**3 балла**
- Есть список рекомендуемых блюд, упорядоченный по приоритету.
- Блюдо с ингредиентом, у которого срок ближе, стоит выше блюда с ингредиентом, у которого срок дальше.

**6 баллов**
- У каждой рекомендации есть объяснение с числами: продукт, номер партии, количество, время до истечения.
- В списке нет ни одного блюда из стоп-листа.
- Список обновляется на открытом экране после заказа, поставки и истечения партии.
- После сброса стенда список не пуст и не абсурден: первым не стоит блюдо, у ингредиентов которого до срока больше недели.
- При одинаковом состоянии склада порядок рекомендаций одинаков при каждом обновлении.

**9 баллов**
- Рекомендация содержит цель: сколько порций продать и до какого времени, и сколько продукта это спасёт.
- Блюдо с небольшим остатком дешёвого истекающего продукта не обгоняет блюдо с большим остатком дорогого истекающего продукта.
- Если один истекающий продукт входит в несколько блюд, суммарная цель по этим блюдам не превышает того, что реально находится под угрозой списания.
- Блюдо не рекомендуется, если его продвижение исчерпает другой, не истекающий ингредиент, которого и так мало; причина показана.
- Продукт, который успеет разойтись при обычном спросе, не делает блюдо горячим.
- В продукте и в README есть измеренное сравнение: на сколько основной алгоритм снижает списания относительно случайных рекомендаций и относительно сортировки по ближайшему сроку, с числом прогонов; сравнение воспроизводится одной командой из README.
- После прыжка времени список остаётся осмысленным: количества под риском не выросли скачком у продуктов, срок которых далеко.

## 4. Стабильность и качество реализации

**3 балла**
- Стенд открывается по ссылке, демо-сценарий проходит от начала до конца без ошибок на экране.
- Проект запускается одной командой из README.

**6 баллов**
- Некорректный запрос (пустой заказ, неизвестное блюдо, отрицательное количество) возвращает ошибку `4xx` единого формата с понятным текстом, а не `500`.
- Генератор событий работает 10 минут на ускоренном времени: нет ответов `500`, экран не зависает, остатки не уходят в минус.
- В репозитории есть автоматические тесты, и в README указана команда, которой они запускаются; на последнем коммите они проходят.
- У каждого экрана есть состояния загрузки, «пусто» и «ошибка».

**9 баллов**
- Пятьдесят одновременных заказов при работающем генераторе: ни одного ответа `500`, ни одной двойной продажи, сумма по журналу движений сходится с остатками.
- Перезапуск сервиса посреди работы генератора: данные на месте, время не ушло назад, экран восстановил связь сам.
- Сброс стенда при работающем генераторе завершается успешно и приводит стенд в одно и то же состояние каждый раз.
- Сброс, прыжок времени и смена скорости недоступны без токена; всё остальное открыто по ссылке.
- В README описаны принятые решения по неоднозначным местам кейса (сроки, единицы, отказ заказа, часовой пояс) и приведены примеры запросов, которые работают на стенде как написано.
- Есть опубликованное описание API, по которому запрос из `curl` проходит с первого раза.

## 5. Приятная вёрстка и дизайн

**3 балла**
- Все экраны открываются и читаются на ноутбуке; тексты и таблицы не наезжают друг на друга.
- Данные показаны в таблицах или карточках, а не сырым JSON.

**6 баллов**
- Единый стиль на всех экранах: одни и те же цвета, шрифты, отступы, компоненты.
- Срочность по сроку годности показана единой цветовой шкалой на складе, в предупреждениях и в горячих предложениях.
- Количества — в человеческих единицах («1,2 кг»), время — относительное («через 14 ч») с точной датой во всплывающей подсказке.
- Время стенда и его скорость видны на каждом экране; ясно, что время симулированное.
- Сообщение об отказе в заказе объясняет человеку, чего не хватает, без кодов ошибок.

**9 баллов**
- Изменения появляются без перезагрузки и заметны глазу: изменившаяся строка или карточка коротко подсвечивается.
- Ключевое действие каждого экрана выполняется не более чем в два клика; путь от предупреждения о партии до блюда, которое её спасёт, — один клик.
- Экраны пригодны на ширине планшета; основные экраны (склад, стоп-лист, горячие предложения) — на телефоне.
- Навигация с клавиатуры работает, у полей есть подписи, контраст текста достаточен.
- Карточка горячего предложения читается за три секунды: блюдо, цель в порциях, срок, причина — без прокрутки и без таблиц.
- Нет ни одного «сырого» места: непереведённых ключей, технических идентификаторов вместо названий, обрезанных текстов, пустых экранов без пояснения.
